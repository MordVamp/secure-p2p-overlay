# Архитектурные решения (журнал ADR)

Решения, принятые в ходе работы над проектом (2026-10-26 … 2026-10-28).
Формат: контекст → решение → почему → компромиссы. Порядок хронологический.
Статус: ✅ реализовано и проверено · ⚠️ реализовано с ограничениями · 📝 только запланировано.

## ADR-01 · Ответы RPC читает отдельная reader-задача на соединение ✅
**Контекст.** Исходящее соединение отправляло запрос и не читало ответ (замечания E1-6, E24–E26).
**Решение.** `spawn_conn_reader` на каждое исходящее соединение; ответы доставляются в `PendingRpc` по `request_id`.
**Почему.** Из двух вариантов преподавателя (читать внутри RPC-операции или отдельная задача с диспетчеризацией) выбрана диспетчеризация: один механизм для PING/FIND_NODE/STORE/FIND_VALUE.
**Компромисс.** Соединение на каждый RPC (без пула) — проще, но больше рукопожатий.

## ADR-02 · NodeID самосертифицирующийся и проверяется везде ✅
**Решение.** `NodeID = SHA-256(0x01 ‖ Ed25519 pubkey)`; пара (NodeID, pubkey) проверяется в PONG, контактах FIND_NODE, STORE, подписи сообщений, `TUNNEL_BUILD` (B3). Контакты с неверной парой отбрасываются.
**Почему.** Не нужен внешний PKI; подмена ключа под чужим NodeID невозможна.

## ADR-03 · Туннель: приёмник outbox хранится в сессии (B6) ✅
**Контекст.** `_rx` отбрасывался → `send` падал с «channel closed»; в сессии был не тот `tunnel_id`.
**Решение.** `TunnelSession::with_id`, `attach_outbox`/`take_outbox`; `new()` сохранён для совместимости тестов.
**Компромисс.** Receiver за `Mutex<Option<…>>` — чуть тяжелее, зато без изменения публичного конструктора.

## ADR-04 · Статус исправлений ведётся в отдельном файле и дублируется в CHANGELOG ✅
`docs/dev/FIXED_REVIEW_COMMENTS.md` + запись в `CHANGELOG.md`. Дублирование — намеренное (по просьбе автора): один файл — одна страница для защиты.

## ADR-05 · GUI — встроенный HTTP-сервер без новых зависимостей ✅
**Решение.** `src/gui/http.rs` поверх `tokio::TcpListener`; две страницы (`node.html`, `orch.html`); два режима: панель узла (`--gui-port`) и GUI оркестратора, который запускает/останавливает узлы.
**Почему.** Не тянуть web-фреймворк ради ~10 эндпоинтов; GUI опционален (без флага выключен).
**Безопасность.** Слушает только `127.0.0.1`; изменяющие действия — только POST.
**Ограничение.** Нет аутентификации (допустимо для localhost-стенда).

## ADR-06 · Сообщения: Messenger встроен в узел, relay пересылает данные ✅
`Messenger` подключён к `Node`; конечный узел туннеля отдаёт данные в `app_sink`; relay держит таблицу пересылки (`TunnelRoutes`). Подпись сообщения проверяется по ключу **из самого сообщения**, привязанному к `from` через NodeID (не зависит от таблицы маршрутизации).

## ADR-07 · DHT-записи подписаны публикатором; first-writer-wins ✅
`DhtRecord` несёт `publisher_key` и подпись; принимающий узел проверяет подпись и TTL ограничивает политикой узла. Чужой живой ключ не перезаписывается.
**Компромисс.** Squatting ключа живым публикатором возможен до истечения TTL.

## ADR-08 · Эксперименты: только реальные данные, воспроизводимый прогон ✅
**Контекст.** Старые сценарии 02–09 генерировали числа через `$RANDOM` (нарушение §22 ТЗ).
**Решение.** Приёмка этапов 1–2 — одна команда `p2p-orchestrator acceptance` (N узлов, сходимость, выгрузка таблиц, контрольные lookup, отказ bootstrap). Коммит `HEAD`, N, параметры пишутся в `summary.md`.
**Корректировка.** Сценарии 02–09 сначала были удалены целиком, затем **восстановлены**: они относятся к этапам 3+, и удалять нужное ТЗ было неверно. Недостоверные данные нужно помечать, а не удалять код.

## ADR-09 · Логи не хранятся в git; история очищена ✅
**Решение.** Логи узлов приёмки пишутся в `logs/<имя_прогона>/` (каталог в `.gitignore`); 13 файлов `node-71xx.log` удалены из **всей** истории (`git filter-branch` + `gc --prune=now`).
**Цена.** Хеши коммитов изменились → нужен `git push --force`. Клоны, уже скачавшие старую историю, придётся пересоздать.
**Остаточный риск.** GitHub может кэшировать старые коммиты по прямым ссылкам.
**Вне git остаются** приватные ключи (`state/`).

`docs/test_vectors/nodeid_xor.json` — публичные синтетические данные (ключи `0101…`), посчитаны независимо на Python. Это проверка формулы, секретов нет. Реальные NodeID живых узлов в репозиторий не кладутся.

## ADR-11 · TLS 1.3 включён на уровне `dial()` и accept ⚠️
**Контекст.** `security/tls.rs` существовал, но нигде не вызывался: весь трафик шёл по голому TCP.
**Решения.**
- **NodeID пира берётся из SPKI сертификата** (x509-parser, только Ed25519): `SHA-256(0x01‖pk)` — совпадает с identity NodeID. Прежний суррогат (хеш DER) не мог совпасть.
- **TLS-контекст общий на процесс** (`rpc::install_tls`, `OnceLock`). Альтернатива — протаскивать через сигнатуры RPC; отвергнута как слишком инвазивная. Допущение: один узел на процесс.
- **`dial()` возвращает `FramedStream<BoxedIo>`** (динамическая диспетчеризация TCP/TLS), без TLS (тесты) — голый TCP.
- **Крипто-провайдер `ring` выбирается явно** — в дереве зависимостей есть и `aws-lc-rs`, без явного выбора узел падал при старте.
- Закрытие без `close_notify` (`UnexpectedEof`) трактуется как обычный EOF.
- PING сверяет NodeID из PONG с ключом TLS.
**Ограничение.** Ожидаемый NodeID сверяется только в PING; остальные RPC шифруются и аутентифицируют ключ, но без сверки с ожидаемым NodeID.

## ADR-12 · DHT: sequence в подписи, TTL-очистка, переопубликование ✅
- `DhtRecord.sequence` входит в подпись (домен `P2P-DHT-RECORD-v2`, несовместим с v1). Откат отвергается; равный sequence допустим только как refresh той же записи.
- `put` выбирает `seq = max(prev+1, now_ms)` — монотонность переживает перезапуск (хранилище в памяти).
- `evict_expired` — раз в 10 с; republish — по `republish_interval_seconds`.
- Своя запись перепубликуется заново, а не повторяется.

## ADR-13 · `NodeRecord` хранится в DHT как значение с префиксом `NREC1` ⚠️
**Решение.** Ключ `SHA-256("node:"‖NodeID)`, значение `NREC1‖msgpack`. Приёмник строго валидирует записи с префиксом: подпись, TTL, привязка к ключу, владелец = отправитель, `pick_newer` против отката `sequence_number`. `NodeRecord` пересоздаётся при каждом republish (свежие `issued_at/expires_at`).
**Почему префикс.** Отличить адресные записи от прикладных данных, не меняя формат DHT-протокола.
**Ограничение.** Чужой публикатор может занять ключ `node:<жертва>` данными **без** префикса (first-writer-wins); смягчается только TTL.

## ADR-14 · Кворум STORE: ≥ 2 из R=3 ✅
`dht.store_quorum` (по умолчанию 2, ограничен `replication_factor`). `put` возвращает ошибку без кворума, локальная копия остаётся (её подхватит republish). Одинокий/первый узел в пустой сети получает «1 из 3» — ожидаемое поведение, запись обновится при следующем цикле.

## ADR-15 · Сквозное шифрование сообщений: sealed box (ECIES) ⚠️
**Решение.** `security/e2e.rs`: эфемерный X25519 отправителя × X25519-ключ получателя (из его Ed25519, Montgomery-форма / `SHA-512(seed)[..32]`) → HKDF-SHA256 → AES-256-GCM; AAD = домен‖`to`‖эфемерный ключ. Подпись Ed25519 внутри `AppMessage` (sign-then-encrypt). Открытый `AppMessage` не принимается.
**Почему sealed box, а не сессия.** Без интерактивного рукопожатия и состояния — работает с асинхронными сообщениями и не требует round-trip через туннель.
**Ключ получателя** берётся из таблицы маршрутизации, иначе из его `NodeRecord` в DHT (отсюда ADR-13).
**Проверено.** 9 unit-тестов + живая отправка A→B через туннель в сети из 6 узлов.
**Ограничения.** Forward secrecy только по стороне отправителя (компрометация долговременного ключа получателя раскрывает прошлый перехват); нет защиты от traffic analysis (размер/время).

## ADR-16 · Негативные тесты — отдельные файлы на область ✅
`test_tls.rs` (7), `test_dht_records.rs` (5), `test_node_record.rs` (11), `test_e2e.rs` (9): подмена/replay-подобные случаи проверяются на реальных сокетах и реальных криптопримитивах, без моков.

## ADR-17 · Защита от петель: счётчик `hops_left` + проверки при BUILD ✅
**Контекст.** Relay знает только следующий hop своего туннеля, полного пути у него нет; зловредный инициатор может построить цикл `A.next=B, B.next=A`, и данные ходили бы по кругу. `max_hops` существовал только в конфиге.
**Решение.**
- Данные: `TunnelDataPayload.hops_left` — как TTL в IP. Отправитель ставит `max_hops+1`, каждый relay уменьшает на 1, при 0 кадр отбрасывается. Отсутствие поля (`serde(default)`) = 0 = «не пересылать» — безопасное значение по умолчанию.
- Построение: `1 ≤ total_hops ≤ max_hops`, `hop_index < total_hops`, `next_hop ≠ инициатор`, `tunnel_id` уникален.
- Builder: уникальные кандидаты.
**Почему счётчик, а не обнаружение цикла.** Обнаружение требует полного пути на каждом relay (раскрывает топологию) или состояния на кадр; счётчик не требует ни того ни другого и ограничивает пересылки жёстко.
**Компромисс.** Формат `TUNNEL_DATA` изменился — несовместим со старыми узлами. Простой цикл по таблицам не обнаруживается, а лишь обрывается через ≤ `max_hops+1` пересылок.

## ADR-18 · APP_ACK — сквозное подтверждение поверх тех же туннелей ✅
**Контекст.** `TUNNEL_ACK` подтверждает только пересылку между соседними hop; он не говорит, что получатель принял и проверил сообщение.
**Решение.** Получатель отвечает отдельным подписанным и зашифрованным `AppMessage` (kind=Ack, payload=id исходного). Отправитель регистрирует ожидание (`oneshot`) до отправки; ACK засчитывается, только если `from` совпадает с адресатом. На ACK ACK не шлётся (нет петель), в inbox он не попадает.
**Почему отдельное сообщение, а не поле ответа.** Туннели однонаправленные, а ответный путь строится независимо; ACK получает те же E2E-гарантии и anti-replay, что и текст.
**Компромиссы.** Обратный туннель строится на первое подтверждение (RTT ≈ 90–180 мс в LAN); ACK сам не подтверждается; без ответа отправитель узнаёт о недоставке только по таймауту.

## ADR-19 · Адрес получателя берётся из результата lookup, а не из таблицы ✅
**Контекст.** Живой тест показал: при малом k корзина может быть полна, и найденный lookup'ом узел не попадает в таблицу → построение туннеля падало с «target unknown».
**Решение.** `deliver()` берёт контакт получателя из `LookupResult.closest`, передаёт в `build_with` как подсказку; пара NodeID/pubkey проверяется. Таблица остаётся запасным источником.
**Урок.** Таблица маршрутизации — кэш для lookup, а не источник истины об адресе; прикладной слой не должен зависеть от её вытеснения.

## ADR-20 · Графики строятся скриптом из CSV и коммитятся вместе с данными ✅
**Решение.** `scripts/analyze.py` пишет PNG и `stats.md` в каталог результатов; PNG хранятся в git как иллюстрации отчёта. Docker не используется (не требуется). Ограничение: графики не проверены визуально, пилотные данные предшествуют TLS/E2E.

## ADR-21 · Живость туннеля = сквозной TUNNEL_ACK; отказ → DEAD → новый маршрут при отправке ✅
**Контекст.** Живой тест (сообщение, пауза 25 с, сообщение) показал, что после простоя доставка ломается навсегда:
`last_ack_ms` hop-ов выставлялся только при построении, поэтому через ~16 с любой туннель становился DEGRADED → DEAD;
`monitor_loop` «восстанавливал» его к **последнему relay** (`hops.last()`), а не к получателю, и без задачи-отправителя —
сообщения копились в канале, который никто не читал.
**Решение.**
- Relay подтверждает `TUNNEL_DATA` только после ACK следующего hop, значит `TUNNEL_ACK` первого relay = кадр прошёл всю
  цепочку. Задача-отправитель сессии на успех обновляет `last_ack_ms` (DEGRADED → ACTIVE), на ошибку переводит туннель в DEAD
  и сообщает результат вызывающему (`TunnelData.done`, oneshot). Ответ ERROR (relay не смог переслать) — тоже отказ.
- Простой — не отказ: давно не подтверждённый туннель → DEGRADED (остаётся пригодным); DEAD — только по ошибке или по TTL
  (туннель заменяется на 90% `tunnel.ttl_seconds`, пока маршрут на relay ещё жив).
- `monitor_loop` удаляет DEAD-туннели; новый маршрут строит `Messenger` при следующей отправке: свежий lookup,
  `TUNNEL_BUILD` без relay, отказавших в предыдущих попытках, повтор того же конверта (одна попытка).
- Узел без маршрута для `tunnel_id` подтверждает кадр, только если E2E-конверт адресован ему (`e2e::recipient`); иначе ERROR.
  Найдено сценарием 07: relay после перезапуска терял таблицу маршрутов и «принимал» чужие кадры как получатель → отправитель
  видел TUNNEL_ACK, но APP_ACK не приходил и туннель не перестраивался.
**Почему не keepalive-проба.** Отказ обнаруживается той же отправкой, которую надо доставить; проба добавила бы трафик и
всё равно не исключила бы гонку «проба прошла → relay упал».
**Компромиссы.** Обнаружение отказа — только при отправке (время обнаружения ≈ connect refused/ACK-таймаут); каждый кадр —
новое TLS-соединение на каждом hop (≈ 20 мс на проход цепочки в debug-сборке, пула соединений нет — ADR-01).
Поле `to` конверта видно relay (оно и раньше было открытым — AAD), теперь его читает и узел-получатель до расшифровки.

## ADR-22 · «Установленная сессия» без lookup; разбивка задержки в ответе `/api/send` ✅
**Контекст.** §15.2 требует раздельно мерить первое сообщение и сообщение по установленной сессии; раньше каждый `send`
делал полный lookup, т.е. «сессии» не было.
**Решение.** `Messenger` кэширует проверенные ключи собеседников (NodeID = hash(ключ) — подделать нельзя; источники: lookup,
входящие подписанные сообщения, NodeRecord). Если туннель пригоден и ключ известен — lookup пропускается.
`send_text_acked` возвращает `SendReport { lookup_ms, tunnel_build_ms, tunnel_send_ms, rebuilt_after_failure, rtt_ms }`;
`tunnel_build_ms = None` ⇔ туннель переиспользован.
**Компромисс.** Если получатель сменил адрес, а туннель ещё жив — первая отправка упадёт и перестроит маршрут через lookup.

## ADR-23 · Локальная история — JSONL в `state_dir` ✅
**Решение.** `app/history.rs`: одна JSON-строка на событие (`out`: delivered/sent/failed с RTT или ошибкой; `in`: received),
файл `history.jsonl` с правами 0600, `/api/history?limit=N`. Без SQLite: append-only, читается любым инструментом,
повреждённая строка пропускается, а не ломает чтение.
**Компромиссы.** Тексты хранятся открыто на диске владельца (рядом с `identity.key` — та же граница доверия); нет ротации
и индексов — чтение хвоста O(размер файла), для курсового объёма достаточно.

## ADR-24 · Подписанный псевдоним = обычная подписанная DHT-запись ✅
**Решение.** Ключ `SHA-256("alias:"||alias)`, значение `ALIAS1:<alias>`; владелец — публикатор `DhtRecord` (подпись покрывает
ключ, NodeID публикатора, sequence и значение; NodeID = hash(ключа)). Публикация отказывает, если псевдоним уже за другим узлом;
хранители — first-writer-wins, пока запись жива; переопубликование — общий механизм `republish_all`.
Отправка принимает `@alias` вместо NodeID. Алфавит `[a-z0-9_-]`, 1–32 символа (без омоглифов и пробелов).
**Почему не отдельный тип записи.** Вся проверка (подпись, привязка NodeID ↔ ключ, откат sequence) уже есть у `DhtRecord`.
**Компромиссы.** Нет глобального арбитража: при разделении сети одно имя могут занять двое; после ухода владельца (TTL 180 с)
псевдоним освобождается. Сравнивать NodeID при первом контакте всё равно нужно (TOFU).

## ADR-25 · Сценарии — Python-драйвер поверх HTTP API узлов, мета-данные в каждом прогоне ✅
**Решение.** `scripts/scenarios.py` запускает реальные `p2p-node`, управляет ими через `/api/*`, пишет `results.csv`,
`summary.md`, `meta.json` (коммит + sha256 незакоммиченного diff, конфигурация, seed, время, N/k/α/R, тайм-ауты, граф).
Отказы — SIGKILL, после инъекции узел перезапускается с той же identity (условия одинаковы). Операционная сходимость —
по §15.1: два контрольных раунда подряд ≥95% lookup из заранее сформированного набора и Δ контактов ≤10%.
`.sh`-сценарии — обёртки над драйвером. pcap снимается `dumpcap` (без root при `cap_net_raw`) с положительным контролем:
тот же маркер обязан найтись в открытом HTTP панели, иначе проверка считается недостоверной.
**Почему Python.** Узлы и вся логика — Rust; драйвер только запускает процессы и считает статистику (Ustnie_Trebovaniya
допускает любой инструмент для скриптов). Приёмка этапов 1–2 по-прежнему на Rust (`p2p-orchestrator acceptance`).
**Ограничение.** Разрешение метода сходимости — пауза 1 с между раундами; все узлы на одной машине.
