# Архитектурные решения (журнал ADR)

Решения, принятые в ходе работы над проектом (2026-10-26 … 2026-11-02).
Формат: контекст → решение → почему → компромиссы. Порядок хронологический.
Статус: ✅ реализовано и проверено · ⚠️ реализовано с ограничениями · 📝 только запланировано.

## ADR-01 · Ответы RPC читает отдельная reader-задача на соединение ✅
**Контекст.** Исходящее соединение отправляло запрос и не читало ответ (замечания E1-6, E24–E26).
**Решение.** `spawn_conn_reader` на каждое исходящее соединение; ответы доставляются в `PendingRpc` по `request_id`.
**Почему.** Из двух вариантов преподавателя (читать внутри RPC-операции или отдельная задача с диспетчеризацией) выбрана диспетчеризация: один механизм для PING/FIND_NODE/STORE/FIND_VALUE.
**Компромисс.** Соединение на каждый RPC (без пула) — проще, но больше рукопожатий.

## ADR-02 · NodeID самосертифицирующийся и проверяется везде ✅
**Решение.** `NodeID = SHA-256(0x01 ‖ Ed25519 pubkey)`; пара (NodeID, pubkey) проверяется в PONG, контактах FIND_NODE, STORE, подписи сообщений, `TUNNEL_BUILD` (B3). Контакты с неверной парой отбрасываются.
**Почему.** Не нужен внешний PKI; подмена ключа под чужим NodeID невозможна.

## ADR-03 · Туннель: приёмник outbox хранится в сессии (B6) ✅
**Контекст.** `_rx` отбрасывался → `send` падал с «channel closed»; в сессии был не тот `tunnel_id`.
**Решение.** `TunnelSession::with_id`, `attach_outbox`/`take_outbox`; `new()` сохранён для совместимости тестов.
**Компромисс.** Receiver за `Mutex<Option<…>>` — чуть тяжелее, зато без изменения публичного конструктора.

## ADR-05 · GUI — встроенный HTTP-сервер без новых зависимостей ✅
**Решение.** `src/gui/http.rs` поверх `tokio::TcpListener`; две страницы (`node.html`, `orch.html`); два режима: панель узла (`--gui-port`) и GUI оркестратора, который запускает/останавливает узлы.
**Почему.** Не тянуть web-фреймворк ради ~10 эндпоинтов; GUI опционален (без флага выключен).
**Безопасность.** Слушает только `127.0.0.1`; изменяющие действия — только POST.
**Ограничение.** Нет аутентификации (допустимо для localhost-стенда).

## ADR-06 · Сообщения: Messenger встроен в узел, relay пересылает данные ✅
`Messenger` подключён к `Node`; конечный узел туннеля отдаёт данные в `app_sink`; relay держит таблицу пересылки (`TunnelRoutes`). Подпись сообщения проверяется по ключу **из самого сообщения**, привязанному к `from` через NodeID (не зависит от таблицы маршрутизации).

## ADR-07 · DHT-записи подписаны публикатором; first-writer-wins ✅
`DhtRecord` несёт `publisher_key` и подпись; принимающий узел проверяет подпись и TTL ограничивает политикой узла. Чужой живой ключ не перезаписывается.
**Компромисс.** Squatting ключа живым публикатором возможен до истечения TTL.

## ADR-11 · TLS 1.3 включён на уровне `dial()` и accept ⚠️
**Контекст.** `security/tls.rs` существовал, но нигде не вызывался: весь трафик шёл по голому TCP.
**Решения.**
- **NodeID пира берётся из SPKI сертификата** (x509-parser, только Ed25519): `SHA-256(0x01‖pk)` — совпадает с identity NodeID. Прежний суррогат (хеш DER) не мог совпасть.
- **TLS-контекст общий на процесс** (`rpc::install_tls`, `OnceLock`). Альтернатива — протаскивать через сигнатуры RPC; отвергнута как слишком инвазивная. Допущение: один узел на процесс.
- **`dial()` возвращает `FramedStream<BoxedIo>`** (динамическая диспетчеризация TCP/TLS), без TLS (тесты) — голый TCP.
- **Крипто-провайдер `ring` выбирается явно** — в дереве зависимостей есть и `aws-lc-rs`, без явного выбора узел падал при старте.
- Закрытие без `close_notify` (`UnexpectedEof`) трактуется как обычный EOF.
- PING сверяет NodeID из PONG с ключом TLS.
**Ограничение.** Ожидаемый NodeID сверяется только в PING; остальные RPC шифруются и аутентифицируют ключ, но без сверки с ожидаемым NodeID.

## ADR-12 · DHT: sequence в подписи, TTL-очистка, переопубликование ✅
- `DhtRecord.sequence` входит в подпись (домен `P2P-DHT-RECORD-v2`, несовместим с v1). Откат отвергается; равный sequence допустим только как refresh той же записи.
- `put` выбирает `seq = max(prev+1, now_ms)` — монотонность переживает перезапуск (хранилище в памяти).
- `evict_expired` — раз в 10 с; republish — по `republish_interval_seconds`.
- Своя запись перепубликуется заново, а не повторяется.

## ADR-13 · `NodeRecord` хранится в DHT как значение с префиксом `NREC1` ⚠️
**Решение.** Ключ `SHA-256("node:"‖NodeID)`, значение `NREC1‖msgpack`. Приёмник строго валидирует записи с префиксом: подпись, TTL, привязка к ключу, владелец = отправитель, `pick_newer` против отката `sequence_number`. `NodeRecord` пересоздаётся при каждом republish (свежие `issued_at/expires_at`).
**Почему префикс.** Отличить адресные записи от прикладных данных, не меняя формат DHT-протокола.
**Ограничение.** Чужой публикатор может занять ключ `node:<жертва>` данными **без** префикса (first-writer-wins); смягчается только TTL.

## ADR-14 · Кворум STORE: ≥ 2 из R=3 ✅
`dht.store_quorum` (по умолчанию 2, ограничен `replication_factor`). `put` возвращает ошибку без кворума, локальная копия остаётся (её подхватит republish). Одинокий/первый узел в пустой сети получает «1 из 3» — ожидаемое поведение, запись обновится при следующем цикле.

## ADR-15 · Сквозное шифрование сообщений: sealed box (ECIES) ⚠️
**Решение.** `security/e2e.rs`: эфемерный X25519 отправителя × X25519-ключ получателя (из его Ed25519, Montgomery-форма / `SHA-512(seed)[..32]`) → HKDF-SHA256 → AES-256-GCM; AAD = домен‖`to`‖эфемерный ключ. Подпись Ed25519 внутри `AppMessage` (sign-then-encrypt). Открытый `AppMessage` не принимается.
**Почему sealed box, а не сессия.** Без интерактивного рукопожатия и состояния — работает с асинхронными сообщениями и не требует round-trip через туннель.
**Ключ получателя** берётся из таблицы маршрутизации, иначе из его `NodeRecord` в DHT (отсюда ADR-13).
**Проверено.** 9 unit-тестов + живая отправка A→B через туннель в сети из 6 узлов.
**Ограничения.** Forward secrecy только по стороне отправителя (компрометация долговременного ключа получателя раскрывает прошлый перехват); нет защиты от traffic analysis (размер/время).

## ADR-16 · Негативные тесты — отдельные файлы на область ✅
`test_tls.rs` (7), `test_dht_records.rs` (5), `test_node_record.rs` (11), `test_e2e.rs` (9): подмена/replay-подобные случаи проверяются на реальных сокетах и реальных криптопримитивах, без моков.

## ADR-17 · Защита от петель: счётчик `hops_left` + проверки при BUILD ✅
**Контекст.** Relay знает только следующий hop своего туннеля, полного пути у него нет; зловредный инициатор может построить цикл `A.next=B, B.next=A`, и данные ходили бы по кругу. `max_hops` существовал только в конфиге.
**Решение.**
- Данные: `TunnelDataPayload.hops_left` — как TTL в IP. Отправитель ставит `max_hops+1`, каждый relay уменьшает на 1, при 0 кадр отбрасывается. Отсутствие поля (`serde(default)`) = 0 = «не пересылать» — безопасное значение по умолчанию.
- Построение: `1 ≤ total_hops ≤ max_hops`, `hop_index < total_hops`, `next_hop ≠ инициатор`, `tunnel_id` уникален.
- Builder: уникальные кандидаты.
**Почему счётчик, а не обнаружение цикла.** Обнаружение требует полного пути на каждом relay (раскрывает топологию) или состояния на кадр; счётчик не требует ни того ни другого и ограничивает пересылки жёстко.
**Компромисс.** Формат `TUNNEL_DATA` изменился — несовместим со старыми узлами. Простой цикл по таблицам не обнаруживается, а лишь обрывается через ≤ `max_hops+1` пересылок.

## ADR-18 · APP_ACK — сквозное подтверждение поверх тех же туннелей ✅
**Контекст.** `TUNNEL_ACK` подтверждает только пересылку между соседними hop; он не говорит, что получатель принял и проверил сообщение.
**Решение.** Получатель отвечает отдельным подписанным и зашифрованным `AppMessage` (kind=Ack, payload=id исходного). Отправитель регистрирует ожидание (`oneshot`) до отправки; ACK засчитывается, только если `from` совпадает с адресатом. На ACK ACK не шлётся (нет петель), в inbox он не попадает.
**Почему отдельное сообщение, а не поле ответа.** Туннели однонаправленные, а ответный путь строится независимо; ACK получает те же E2E-гарантии и anti-replay, что и текст.
**Компромиссы.** Обратный туннель строится на первое подтверждение (RTT ≈ 90–180 мс в LAN); ACK сам не подтверждается; без ответа отправитель узнаёт о недоставке только по таймауту.

## ADR-19 · Адрес получателя берётся из результата lookup, а не из таблицы ✅
**Контекст.** Живой тест показал: при малом k корзина может быть полна, и найденный lookup'ом узел не попадает в таблицу → построение туннеля падало с «target unknown».
**Решение.** `deliver()` берёт контакт получателя из `LookupResult.closest`, передаёт в `build_with` как подсказку; пара NodeID/pubkey проверяется. Таблица остаётся запасным источником.
**Урок.** Таблица маршрутизации — кэш для lookup, а не источник истины об адресе; прикладной слой не должен зависеть от её вытеснения.

## ADR-21 · Живость туннеля = сквозной TUNNEL_ACK; отказ → DEAD → новый маршрут при отправке ✅
**Контекст.** Живой тест (сообщение, пауза 25 с, сообщение) показал, что после простоя доставка ломается навсегда:
`last_ack_ms` hop-ов выставлялся только при построении, поэтому через ~16 с любой туннель становился DEGRADED → DEAD;
`monitor_loop` «восстанавливал» его к **последнему relay** (`hops.last()`), а не к получателю, и без задачи-отправителя —
сообщения копились в канале, который никто не читал.
**Решение.**
- Relay подтверждает `TUNNEL_DATA` только после ACK следующего hop, значит `TUNNEL_ACK` первого relay = кадр прошёл всю
  цепочку. Задача-отправитель сессии на успех обновляет `last_ack_ms` (DEGRADED → ACTIVE), на ошибку переводит туннель в DEAD
  и сообщает результат вызывающему (`TunnelData.done`, oneshot). Ответ ERROR (relay не смог переслать) — тоже отказ.
- Простой — не отказ: давно не подтверждённый туннель → DEGRADED (остаётся пригодным); DEAD — только по ошибке или по TTL
  (туннель заменяется на 90% `tunnel.ttl_seconds`, пока маршрут на relay ещё жив).
- `monitor_loop` удаляет DEAD-туннели; новый маршрут строит `Messenger` при следующей отправке: свежий lookup,
  `TUNNEL_BUILD` без relay, отказавших в предыдущих попытках, повтор того же конверта (одна попытка).
- Узел без маршрута для `tunnel_id` подтверждает кадр, только если E2E-конверт адресован ему (`e2e::recipient`); иначе ERROR.
  Найдено сценарием 07: relay после перезапуска терял таблицу маршрутов и «принимал» чужие кадры как получатель → отправитель
  видел TUNNEL_ACK, но APP_ACK не приходил и туннель не перестраивался.
**Почему не keepalive-проба.** Отказ обнаруживается той же отправкой, которую надо доставить; проба добавила бы трафик и
всё равно не исключила бы гонку «проба прошла → relay упал».
**Компромиссы.** Обнаружение отказа — только при отправке (время обнаружения ≈ connect refused/ACK-таймаут); каждый кадр —
новое TLS-соединение на каждом hop (≈ 20 мс на проход цепочки в debug-сборке, пула соединений нет — ADR-01).
Поле `to` конверта видно relay (оно и раньше было открытым — AAD), теперь его читает и узел-получатель до расшифровки.

## ADR-22 · «Установленная сессия» без lookup; разбивка задержки в ответе `/api/send` ✅
**Контекст.** §15.2 требует раздельно мерить первое сообщение и сообщение по установленной сессии; раньше каждый `send`
делал полный lookup, т.е. «сессии» не было.
**Решение.** `Messenger` кэширует проверенные ключи собеседников (NodeID = hash(ключ) — подделать нельзя; источники: lookup,
входящие подписанные сообщения, NodeRecord). Если туннель пригоден и ключ известен — lookup пропускается.
`send_text_acked` возвращает `SendReport { lookup_ms, tunnel_build_ms, tunnel_send_ms, rebuilt_after_failure, rtt_ms }`;
`tunnel_build_ms = None` ⇔ туннель переиспользован.
**Компромисс.** Если получатель сменил адрес, а туннель ещё жив — первая отправка упадёт и перестроит маршрут через lookup.

## ADR-23 · Локальная история — JSONL в `state_dir` ✅
**Решение.** `app/history.rs`: одна JSON-строка на событие (`out`: delivered/sent/failed с RTT или ошибкой; `in`: received),
файл `history.jsonl` с правами 0600, `/api/history?limit=N`. Без SQLite: append-only, читается любым инструментом,
повреждённая строка пропускается, а не ломает чтение.
**Компромиссы.** Тексты хранятся открыто на диске владельца (рядом с `identity.key` — та же граница доверия); нет ротации
и индексов — чтение хвоста O(размер файла), для курсового объёма достаточно.

## ADR-24 · Подписанный псевдоним = обычная подписанная DHT-запись ✅
**Решение.** Ключ `SHA-256("alias:"||alias)`, значение `ALIAS1:<alias>`; владелец — публикатор `DhtRecord` (подпись покрывает
ключ, NodeID публикатора, sequence и значение; NodeID = hash(ключа)). Публикация отказывает, если псевдоним уже за другим узлом;
хранители — first-writer-wins, пока запись жива; переопубликование — общий механизм `republish_all`.
Отправка принимает `@alias` вместо NodeID. Алфавит `[a-z0-9_-]`, 1–32 символа (без омоглифов и пробелов).
**Почему не отдельный тип записи.** Вся проверка (подпись, привязка NodeID ↔ ключ, откат sequence) уже есть у `DhtRecord`.
**Компромиссы.** Нет глобального арбитража: при разделении сети одно имя могут занять двое; после ухода владельца (TTL 180 с)
псевдоним освобождается. Сравнивать NodeID при первом контакте всё равно нужно (TOFU).

## ADR-25 · Сценарии — Rust-драйвер в оркестраторе поверх HTTP API узлов, мета-данные в каждом прогоне ✅ (пересмотрено 02.11)
**Решение.** `p2p-orchestrator scenario <01..09|pcap|all>` (`src/experiment/`) запускает реальные `p2p-node`, управляет ими
через `/api/*`, пишет `results.csv`, `summary.md`, `meta.json` (коммит + sha256 незакоммиченного diff, конфигурация, seed,
время, N/k/α/R, тайм-ауты, граф), графики `plots/` и журналы узлов `node_logs/` (без ANSI, пути относительные).
Отказы — SIGKILL, после инъекции узел перезапускается с той же identity (условия одинаковы). Операционная сходимость —
по §15.1: два контрольных раунда подряд ≥95% lookup из заранее сформированного набора и Δ контактов ≤10%.
По умолчанию N=15 (Ustnie_Trebovaniya §2: 13–15, ближе к верхней границе). `.sh`-сценарии — обёртки над оркестратором.
pcap снимается `dumpcap` (без root при `cap_net_raw`) с положительным контролем: тот же маркер обязан найтись в открытом
HTTP панели, иначе проверка считается недостоверной.
**Почему Rust.** Ustnie_Trebovaniya §8: «ТЗ может упоминать Python для скриптов/графиков — игнорируем, всё делаем на Rust»
(bash-скрипты допустимы). Первая версия драйвера (28.10) была на Python, а в этом ADR ошибочно утверждалось, что устные
требования допускают любой инструмент; 02.11 драйвер перенесён в `p2p-orchestrator`, где уже были запуск узлов и HTTP-клиент
(приёмка этапов 1–2). Python-версия сохранена запасной (`scripts/python/scenarios.py`, тот же метод, `driver` в `meta.json`).
Результаты 29.10 (Python, N=12) оставлены в `experiments/results/*/20261029_*` как предыдущий прогон.
**Ограничение.** Разрешение метода сходимости — пауза 1 с между раундами; все узлы на одной машине.

## ADR-26 · Lookup не возвращает инициатора; кворум STORE — по различным узлам ✅
**Контекст.** Сценарий 04 на N=15: в строках с `stored_on=4` (автор + 3 подтверждения) реплик, кроме автора, было 2.
Причина — пир отвечает на FIND_NODE ближайшими из своей таблицы, исключая только себя; спрашивающий в ответ попадает.
Инициатор добавлял свой контакт в кандидаты, опрашивал сам себя и, если оказывался среди R ближайших к ключу, отправлял
STORE сам себе — это засчитывалось как отдельная реплика, и кворум «≥2 из 3» (§10.1) выполнялся без второго узла.
**Решение.** `IterativeLookup` не добавляет свой NodeID из ответов пиров (как в Kademlia: узел не ищет сам себя).
STORE уходит на R ближайших *других* узлов, локальная копия считается отдельно — кворум теперь по различным узлам.
**Проверка.** `tests/test_lookup_self.rs`: пир B возвращает A, lookup A → A не в результате и не опрошен; без исправления тест падает.
**Следствие.** Результаты сценариев, снятые до исправления (`20261029_*`, Python, N=12), чуть завышают RPC на lookup и
допускают «реплику у автора»; актуальные — `20261102_*`.

## ADR-27 · Собственное рукопожатие (AKE) — вариант канала рядом с TLS ✅
**Контекст.** ТЗ §11.3 (продвинутый уровень): учебная схема установления сессии из библиотечных примитивов. TLS должен
остаться: на нём сняты все данные упрощённого уровня.
**Решение.** `security.channel: tls | ake` (флаг `--channel`); `security/ake.rs` — подписанный Диффи–Хеллман: Hello / Reply
(подпись ответчика) / Finish (подпись инициатора) над каноническим транскриптом из всех полей §11.3, ключи направлений
через HKDF-SHA256 от X25519 эфемерных ключей, записи AES-256-GCM с монотонным счётчиком, ключи обнуляются при закрытии.
AKE реализован как `AsyncRead + AsyncWrite`, поэтому `dial()` и accept выбирают вариант, а всё выше транспорта не меняется.
Тесты §11.4 — `tests/test_ake.rs` (10): MITM подменяет эфемерный ключ, поля Reply, байт шифртекста; повтор записи в
текущей сессии; запись из завершённой сессии; подмена identity-ключа; несоответствие NodeID.
**Найдено при измерениях.** (1) Первая версия была в ≈ 10 раз медленнее TLS: два мелких `write` подряд (длина, затем тело)
и отдельный сегмент Finish ловили алгоритм Нейгла + delayed ACK (≈ 40 мс на соединение). Исправлено: сообщение одной
записью, Finish уходит одним сегментом с первой записью инициатора, как Finished и данные в TLS 1.3 (без TCP_NODELAY,
чтобы условия совпадали с TLS). (2) Оставшийся разрыв в debug-сборке — неоптимизированная криптография на кривых
(curve25519-dalek на чистом Rust), тогда как rustls/ring — оптимизированный C/asm даже в debug. В release AKE ≈ TLS
(сценарий `channel`).
**Компромиссы.** Идентичность сторон не скрывается (в отличие от TLS 1.3); нет возобновления сессий; вся сеть на одном
варианте — согласования нет.

## ADR-28 · Байтовые поля — MessagePack bin ✅
**Контекст.** rmp-serde по умолчанию кодирует `Vec<u8>` массивом чисел: байт ≥ 128 — 2 байта, в среднем +50%. Для
блока файла 40 КиБ конверт вырастал до ≈ 90 КиБ и не влезал в сегмент туннеля.
**Решение.** Общий `protocol::payload::encode` пишет байтовые поля как bin (`BytesMode::ForceIterables`); E2E-конверт,
AKE и NodeRecord кодируются им же. Декодер читает оба представления.
**Следствие.** Сообщения стали короче, поэтому контрольный повтор сценариев упрощённого уровня сделан на финальном коде.
`NodeId` (массив фиксированной длины) по-прежнему массив — режим его не затрагивает.

## ADR-29 · Передача файлов поверх тех же подписанных E2E-сообщений ✅
**Решение.** Четыре новых `MessageKind` (FileOffer/Block/Ack/Done) в существующем `AppMessage`: та же подпись, конверт,
туннель, анти-replay, история. Блоки по 40 КиБ, окно 8 с подтверждением и повтором пропущенных, итоговая проверка
SHA-256 у получателя, приём только в `downloads/`, лимит, тайм-аут неполного файла (`app/files.rs`, `tests/test_files.rs`).
**Почему не отдельный поток.** Туннель однонаправленный и подтверждает каждый кадр; повторное использование конвертов
даёт все гарантии без нового протокола.
**Компромиссы.** Блоки внутри окна идут последовательно (каждый ждёт TUNNEL_ACK) — goodput ограничен RTT цепочки и
стоимостью подписи и шифрования на блок; возобновление не реализовано; `/api/send_file` читает любой файл, доступный
процессу узла (API только локальный, без аутентификации — THREAT_MODEL).

## ADR-30 · Пул туннелей, профили кандидатов, стратегии выбора ✅
**Решение.** `TunnelManager` держит до `pool_size` туннелей на получателя; резервные строятся в фоне на непересекающихся
relay; при отказе основного тот же кадр сразу уходит по резервному — время обнаружения и переключения попадает в отчёт.
Профили (`tunnel/profile.rs`) — все поля §12; стратегии `closest | random | rating`. Виновный в обрыве определяется по
тексту ошибки: relay дописывает адрес следующего hop и причину с дальнего конца, берётся самое глубокое упоминание.
**Почему так.** Без определения виновного отказ одного relay «штрафует» и исправных соседей по туннелю, и рейтинг
перестаёт различать узлы.
**Компромиссы.** Задержка в профиле — среднее по hop туннеля (точно по hop измеряется только TUNNEL_BUILD); при
`pool_size = 1` поведение совпадает с упрощённым уровнем.

## ADR-31 · Внесение отказов на ретрансляторе — только для экспериментов ✅
**Решение.** `--fault-drop P` (с вероятностью P ретранслятор отвечает ERROR вместо пересылки) и `--fault-delay-ms D`
(задержка пересылки). По умолчанию выключено; при включении узел пишет предупреждение в журнал.
**Почему.** На одной машине все узлы одинаково надёжны — сравнивать стратегии выбора не на чем.
**Компромиссы.** Модель отказа простая (немедленный отказ, а не молчание); с `drop` сценарий быстрый, «молчащий» relay
дал бы тайм-ауты по 5 с.

## ADR-32 · Сверка NodeID во всех соединениях и окно анти-replay на диске ✅
**Решение.** (1) `dial_expect` с ожидаемым NodeID везде, где он известен: RPC к контактам, TUNNEL_BUILD, первый hop,
relay → следующий hop (NodeID запоминается в маршруте при TUNNEL_BUILD). (2) Анти-replay — окно 10 минут по подписанной
метке времени + принятые `message_id` в `<state_dir>/replay.log`, загружаются при старте (`app/replay.rs`).
**Было.** NodeID сверялся только в PING; множество принятых id жило в памяти и очищалось при 4096.

## ADR-33 · Ограниченный underlay и netem на одной машине ✅ (код), ⏳ (прогон — нужен root)
**Решение.** Узлы получают разные loopback-адреса (`--host 127.0.1.x / 127.0.2.x / 127.0.3.x`) и привязывают к ним
исходящие соединения; nftables (`reject with tcp reset`) запрещает трафик между 127.0.1.0/24 и 127.0.2.0/24, шлюзы в
127.0.3.0/24 видят всех — сценарий `underlay`. Деградация — `tc qdisc … netem` на lo, сценарий `10`. Оба вызывают
`sudo -n` (сначала `sudo -v`), правила снимаются при любом исходе, файлы результатов остаются у пользователя.
**Почему reject, а не drop.** С drop каждая попытка соединения в чужую группу ждёт тайм-аут подключения (3 с) — прогон
растягивается в десятки раз; недостижимость при этом та же.
**Ограничение.** Механика проверена без правил (`P2P_UNDERLAY_DRY=1`); прогоны с root в этой работе выполняет пользователь.

## ADR-34 · Android: настоящий узел на телефоне, а не пульт к компьютеру ✅
**Решение.** В APK кладётся тот же `p2p-node`, кросс-компилированный под `aarch64/x86_64-linux-android`
(`android/build_node.sh`, NDK), как исполняемый `libp2pnode.so` в `jniLibs` — Android разрешает exec только из
`nativeLibraryDir`. Foreground-сервис запускает его как процесс; интерфейс (Kotlin, Jetpack Compose) работает через тот же
локальный HTTP API, что веб-панель и `p2p-desktop`. Подключение к ПК — ссылка `p2p-overlay://IP:порт?id=NodeID` (QR в desktop):
адрес → bootstrap, NodeID → контакт.
**Почему не «пульт».** Пульт к API компьютера потребовал бы открыть API в сеть (аутентификация, CSRF, TLS к API) и не
добавил бы телефона в оверлей: сообщения шли бы от NodeID компьютера. Узел на телефоне получает свой ключ, свои туннели
и проверяет протокол на второй платформе без единой строки протокольного кода на Kotlin.
**Почему не JNI.** Узел и так рассчитан на работу отдельным процессом с API; JNI-обёртка дала бы второй интерфейс к тем же
функциям и общий процесс (падение узла роняло бы интерфейс).
**Сопутствующие изменения.** (1) `node.advertise_host` / `--advertise auto|IP`: при `listen_host = 0.0.0.0` узел раньше всегда
анонсировал `127.0.0.1` — для другого устройства это недостижимый адрес. `auto` перебирает интерфейсы (`getifaddrs`)
и берёт частный адрес на физическом Wi-Fi/Ethernet: маршрут по умолчанию на машине автора идёт через VPN-tun, и простой
приём «UDP connect → local_addr» выбрал бы адрес туннеля. (2) `/api/status` отдаёт `link`. (3) Desktop: «Локальная сеть»
и «Ретрансляторы» — туннелю нужно ≥ 2 relay, а в сети «телефон + ПК» их нет.
**Компромиссы.** APK ≈ 25 МБ (два ABI по 6–7 МБ). Устройства должны видеть друг друга по IP — NAT traversal нет, как и
в остальном оверлее. Эмулятор за NAT проверяется через `adb forward` (узел телефона анонсирует `127.0.0.1`).
**Проверено.** Эмулятор Android 15 + 4 узла на ПК: сообщения в обе стороны с APP_ACK; файл 1.18 МБ в обе стороны,
SHA-256 совпал (11.11.2026).

## ADR-35 · Офлайн-доставка через почтовые ящики DHT ✅
**Решение.** Недоставленное сообщение отправитель шифрует для получателя (тот же E2E-конверт) и публикует подписанной
записью DHT `mbox:<получатель>:<отправитель>`; очередь — `outbox.json`. Получатель раз в `mailbox.poll_interval_s` читает
ящики собеседников из истории (и `/api/watch`) и отвечает обычным APP_ACK; отправитель по ACK убирает письмо (PROTOCOL §7.7).
**Почему так, а не узел-маяк.** Нужна доставка, когда получателя нет в сети или к нему нельзя подключиться (телефон за
NAT), без выделенного сервера. Ящик живёт на тех же R=3 узлах DHT, письмо получатель забирает исходящими запросами.
Один ящик на пару «отправитель → получатель» с единственным публикатором: чужая запись под этим ключом отбрасывается
(подпись не владельца), а значит её нельзя подменить; затереть — можно, это задержка, а не подделка.
**Компромиссы.** Запись живёт, пока отправитель в сети (republish, TTL 180 с); хранители видят, кто кому пишет (ключ
ящика); опрос ящиков — это lookup на каждого собеседника, поэтому период зависит от режима телефона (30 с … 5 мин), а в
экспериментах ящики выключены (`--mailbox-poll 0`), чтобы метрики оставались сопоставимыми.

## ADR-36 · «Только клиент» и режимы энергопотребления телефона ✅
**Решение.** `tunnel.relay: false` (`--no-relay`): узел не пересылает чужой трафик и сообщает это флагом `relay` в своём
`Contact` (по умолчанию `true` — старые записи совместимы); инициаторы не берут такие узлы в цепочку, сам узел отказывает в
TUNNEL_BUILD с `next_hop`. Android: три режима — Эконом (только клиент, без wake lock, редкие refresh и ящики), Обычный,
Максимум (wake lock, пул из 2 туннелей, частые ящики); события для интерфейса и уведомлений — push (`/api/events`).
**Почему.** Ретрансляция и постоянная блокировка сна — основные расходы батареи и трафика телефона; при этом телефон
должен оставаться адресатом. Флаг в контакте, а не только отказ: иначе инициаторы тратили бы попытки построения.
**Компромиссы.** Флаг сообщают третьи узлы в FIND_NODE — злоумышленник может «пометить» честный узел клиентом и сузить
выбор ретрансляторов; это не сильнее, чем просто не вернуть узел в ответе (Eclipse, см. остаточные риски).

## ADR-37 · «Печатает», отчёты о прочтении, группы — опции на прикладном уровне ✅
**Решение.** Новые типы `AppMessage` (8 Typing, 9 Read, 10 GroupText), подписанные и зашифрованные как текст.
«Печатает» уходит только по уже открытому туннелю (ради индикатора туннель не строится) и не чаще раза в 4 с; отчёт о
прочтении — строка-обновление истории, применяется только к своим сообщениям тому же собеседнику; группа существует у
клиентов: состав едет в каждом сообщении, отправитель шлёт копию каждому.
**Почему.** Без изменения туннелей и DHT; каждое сообщение группы защищено так же, как личное. Обе «болтливые» функции —
опции (метаданные о поведении пользователя, лишние конверты).
**Компромиссы.** Групповая рассылка — N конвертов вместо одного; исключить участника нельзя (групповых ключей нет).

## ADR-38 · Секреты на телефоне: токен API, ключ узла под Keystore, блокировка ✅
**Решение.** (1) `P2P_API_TOKEN`: при заданном токене каждый `/api/*` требует `X-Api-Token`; приложение передаёт токен узлу
через окружение. (2) `P2P_IDENTITY_KEK`: узел хранит ключ только как `identity.key.enc` (AES-256-GCM), существующий открытый
ключ шифрует и удаляет; KEK генерирует приложение и хранит обёрнутым ключом Android Keystore. (3) Блокировка приложения
(BiometricPrompt: биометрия или PIN устройства). (4) Номер безопасности пары NodeID для сверки ключа собеседника.
**Почему.** На телефоне `127.0.0.1` доступен всем установленным приложениям — без токена любое из них могло бы писать от
имени владельца. Файл ключа на устройстве переживает бэкап и root-доступ — Keystore делает его бесполезным вне устройства.
**Компромиссы.** Desktop токен и KEK пока не использует (локальная машина пользователя); потеря данных Keystore (сброс
блокировки экрана на некоторых устройствах) делает ключ узла невосстановимым — NodeID придётся сменить.

## ADR-39 · Пул соединений между узлами как режим (`transport.reuse_connections`) ✅
**Решение.** Все исходящие запросы идут через `rpc::pool::request`. При `reuse_connections: false` (по умолчанию) —
новое соединение на каждый запрос, как раньше (ADR-01); при `true` — одно TLS/AKE-соединение к соседу на много
запросов: запись пула = «адрес + ожидаемый NodeID», ответы по `request_id`, закрытие по простою и переполнению, один
повтор по новому соединению при обрыве до ответа. Сервер всегда обрабатывает кадры соединения одновременно (≤ 64)
и закрывает простаивающее соединение через `idle_timeout_ms`, недочитанный кадр — через `read_timeout_ms`.
**Почему.** Замер шага 0 плана звонков ([TRANSPORT_OPTIONS.md](TRANSPORT_OPTIONS.md)): при соединении на каждый кадр
каждый узел цепочки проходит рукопожатие; на debug-сборке круг по цепочке ≈ 23 мс при интервале голосового потока
20 мс — очередь туннеля растёт до 1,2 с. ТЗ §6 допускает оба подхода при описании в ARCHITECTURE.md и одинаковом
режиме в демонстрации.
**Результат (release, N=15, 11.11.2026; через пул — весь трафик, до ADR-40; актуальные прогоны — TRANSPORT_OPTIONS §9).**
Голосовой поток: задержка в одну сторону 5,1 → 1,7 мс (медиана);
сценарий 06: первое сообщение 27 → 10,5 мс, установленная сессия 9 → 3 мс; сценарий 07: восстановление после отказа
ретранслятора 25,2 → 7,5 мс, 10/10 в обоих режимах.
**Компромиссы.** Подробно — [TRANSPORT_OPTIONS.md §8](TRANSPORT_OPTIONS.md) (14 пунктов): больше окно для DoS
(долгий простой, параллельные запросы — поэтому только при пуле), «полуоткрытые» соединения (после тайм-аута ответа
соединение закрывается), блокировка «голова очереди» на общем TCP, повторы могут дублировать, ресурсы держатся дольше,
больше состояния и гонок, метрики зависят от «тёплого» пула. Переиспользуемое соединение не «проверяется заново» —
поэтому ключ пула включает ожидаемый NodeID. По умолчанию оставлен прежний режим: результаты 01–10 сняты на нём.

## ADR-40 · Пул только для туннелей, DHT — соединение на каждый запрос (`transport.pool_scope`) ✅
**Решение.** При включённом пуле `pool_scope: tunnels` (по умолчанию): через пул идут TUNNEL_BUILD и TUNNEL_DATA к
соседям по цепочке, а PING, FIND_NODE, STORE, FIND_VALUE — по соединению на каждый запрос. `all` — всё через пул
(для сравнения). Класс запроса передаётся в `pool::request` (`Scope::Tunnel` / `Scope::Dht`).
**Почему.** DHT — редкие запросы к разным узлам: держать с ними соединения бессмысленно, это ресурсы и окно атаки без
выигрыша. Туннели — частые запросы к одним и тем же соседям: здесь пул и даёт ускорение. Соединения держатся только с
узлами, которые мы сами выбрали ретрансляторами. Заодно DHT-сценарии 01–04 сравнимы с прежними результатами.
**Результат.** Голосовой поток — как при «всё через пул» (1,6 мс против 4,5 мс без пула); сессия 8 → 3 мс; первое
сообщение 26,5 → 19 мс (при «всё» — 8,5 мс: lookup и обратный туннель получателя идут через DHT без пула)
([TRANSPORT_OPTIONS.md §9](TRANSPORT_OPTIONS.md)).
**Компромиссы.** Первое сообщение медленнее, чем при «всё через пул»; два пути соединения в коде.

## ADR-41 · Пул для туннелей — режим по умолчанию ✅
**Решение.** С 11.11.2026 `transport.reuse_connections: true`, `pool_scope: tunnels` во всех конфигах (основной,
продвинутый, Android); прежний режим — `config/node_config_per_request.yaml` или `--no-reuse-connections`.
**Почему.** Пул ускоряет туннели в ~3 раза (ADR-39, ADR-40), а при `pool_scope: tunnels` поведение DHT не меняется —
результаты сценариев 01–05 и 09 остаются действительными. Сценарии с туннелями (06, 07, failover, strategy, files,
channel, pcap) перепрогнаны в новом режиме; в `meta.json` каждого прогона — поле `connections`.
**Найдено при перепрогоне.** С пулом и каналом AKE первое сообщение занимало 280 мс против 20 мс у TLS (release), без
пула — 31 против 30 мс. Причина — алгоритм Нейгла с отложенным ACK: в долгом соединении небольшая запись ждёт
подтверждения предыдущей (до 40 мс), а AKE отправляет кадр больше 16 КиБ несколькими записями. Исправление —
`TCP_NODELAY` на всех сокетах узла (исходящих и входящих); после него AKE и TLS совпадают (первое сообщение 25 / 26 мс).
Все прогоны 11.11 сняты после исправления.
**Компромиссы.** Недостатки пула (TRANSPORT_OPTIONS §8) теперь действуют по умолчанию; демонстрация и прогоны — в одном
режиме для всей сети (ТЗ §6).

## ADR-42 · Кэш замены корзин и повтор bootstrap ✅
**Решение.** (1) У каждой корзины — кэш замены до 8 узлов (Kademlia §2.4): не поместившиеся в полную корзину и
увиденные в ответах FIND_NODE. Они занимают место удалённого контакта и вместе с таблицей служат кандидатами в
ретрансляторы. (2) Bootstrap повторяется (1, 2, 4 … 30 с), пока не ответит хотя бы один узел; при опустевшей таблице —
повторный bootstrap на очередном refresh.
**Почему.** `routing.update` при полной корзине возвращал «старейший для проверки», но lookup это значение игнорировал:
новые узлы терялись, контакты из ответов в таблицу не попадали. При k = 3 у недавно вошедшего узла было 3 контакта —
без отказавшего узла и адресата не набрать 2 ретранслятора (наблюдалось при перепрогоне 07: APP_ACK не уходил ~1 мин).
Узел, стартовавший раньше seed, оставался вне сети навсегда.
**Компромиссы.** Узлы в кэше живость не подтверждали — неудачный выбор такого ретранслятора стоит одной попытки
построения (до 3). Злоумышленник, отвечающий на FIND_NODE своими узлами, может заполнить кэши — это не сильнее
существующего риска Eclipse; выбор по рейтингу (`rating`) понижает таких кандидатов после отказов.
**Проверка.** `tests/test_replacement_cache.rs` (4), `tests/test_bootstrap_retry.rs`.

## ADR-43 · Звонки: TUNNEL_MEDIA, сигнализация, ключ звонка (шаги 2–4 плана) ✅
**Решение.** (1) Кадр TUNNEL_MEDIA (0x16): ретранслятор пересылает сразу через пул и не отвечает, получатель не
подтверждает, отправитель шлёт мимо очереди туннеля «по одному» (`TunnelManager::send_media`). (2) Сигнализация —
подписанные E2E-сообщения CallOffer / CallAnswer / CallReject / CallHangup, «занято», тайм-аут 30 с, запись в историю.
(3) Ключ звонка: одноразовые X25519 обеих сторон в подписанных Offer/Answer → HKDF-SHA256 → по ключу AES-256-GCM на
направление; nonce — направление и номер кадра; окно повторов на 64 номера (PROTOCOL §7.8).
**Почему.** Замер шага 0: кадры туннеля ждут сквозного подтверждения по одному — при круге по цепочке дольше 20 мс
очередь растёт; кроме того, каждое сообщение — X25519 и подпись Ed25519. Голосу не нужны ни подтверждения, ни повторы, а
ключ одной договорённости на звонок дешевле и даёт прямую секретность звонка.
**Результат** (сценарий `call`, N = 15, 5 звонков): установление — 72 мс (release) / 185 мс (debug); задержка медиа в одну
сторону — 0,6 мс / 1,9 мс (путь `media` с подтверждениями: 1,6 / 24 мс); потерь и отвергнутых кадров нет.
**Компромиссы.** Потерянный кадр не повторяется (так и нужно голосу); медиакадры не подписаны — подлинность даёт ключ,
выведенный из подписанных одноразовых ключей; размер и ритм кадров видны ретрансляторам (выравнивания нет). Звук —
ADR-44.
**Проверка.** `tests/test_calls.rs` (6, в т.ч. сквозной звонок с «занято» на живых узлах).

## ADR-44 · Звук звонка в узле, групповой звонок «каждый с каждым», адаптивный буфер (шаги 5–10 плана) ✅
**Решение.** (1) Кодек Opus (16 кГц, 20 мс, 24 кбит/с, FEC), джиттер-буфер, восстановление потерь и смешивание — в узле
(`src/app/voice.rs`); клиент (Android, desktop) отдаёт PCM микрофона и играет PCM от узла через локальный UDP-канал
на 127.0.0.1 с токеном (PROTOCOL §7.8). (2) Групповой звонок до 5 участников — сетка ног «каждый с каждым» с общим id
сеанса, а не звезда через инициатора. (3) Буфер адаптивный: цель по джиттеру RFC 3550 + добавка после опозданий с
растяжением звука (как NetEq). (4) Отчёт получателя CallReport раз в 5 с: потери → избыточность FEC, круг по туннелю →
RTT/2 для оценки качества. (5) Качество — E-модель ITU-T G.107 (MOS), показывается в приложениях.
**Почему.** Одна реализация на Rust для телефона и компьютера; узел уже знает номера кадров и потери; Kotlin и egui
остаются только с микрофоном и динамиком (на Android — системное эхоподавление VOICE_COMMUNICATION). Звезда заставила бы
инициатора расшифровывать чужой голос и обрывала бы звонок при его уходе; при 5 участниках сетка — 4 потока по
~30 кбит/с в каждую сторону, для LAN немного. Метки времени отправителя на разных устройствах дают не задержку, а
расхождение часов (на эмуляторе — 180 мс вместо 37), поэтому для качества — RTT/2.
**Результат** (сценарий `voice`, N = 15: 10 звонков 1:1 и 5 групповых по 3; каждый участник играет свой тон, проверяется,
что слышны ровно тоны собеседников): 15/15; release — установление 62 мс, «рот — ухо» 68 мс, потерь 0, MOS 4,1; debug —
315 мс, 81 мс, 0, 4,1. На эмуляторе Android: звонок телефон ↔ ПК и групповой на 4 — MOS 4,0–4,1; без добавки после
опозданий телефон терял 5,8% кадров («опоздали к такту»: такт задаёт неровный виртуальный микрофон), с добавкой — 0.
**Компромиссы.** Звук между клиентом и узлом — несжатый PCM по loopback (512 кбит/с, только внутри устройства).
Смешивание без нормализации громкости. Ie/Bpl для Opus — допущение (у ITU нет табличных значений): абсолютный MOS —
ориентир, сравнение режимов — корректно. Сетка не масштабируется за 5–6 участников (там нужен SFU).
**Проверка.** `app::voice` (6 модульных: Opus, FEC, маскировка, буфер, углубление после опозданий, E-модель, токен),
`tests/test_calls.rs::voice_one_to_one_group_mesh_and_local_audio_link`, сценарий `voice`.

## ADR-45 · Защита узла от чужой нагрузки: согласие на файлы, квоты, пределы ✅
**Решение.** (1) Файл от незнакомого узла или больше 16 МиБ принимается только после согласия пользователя
(`files.accept = known`; `ask` — всегда, `auto` — эксперименты), до согласия на диск ничего не пишется, без ответа 120 с —
отказ. Квоты места и одновременных приёмов (PROTOCOL §7.5). (2) Ведро токенов на отправителя для «заметных» сообщений
(текст, вызов, предложение файла, «печатает», прочтение): 5/с, запас 30. (3) Входящих соединений не больше 1024 и 64 с
адреса. (4) Квота на публикатора в DHT-хранилище (1/16) и на инициатора в таблице маршрутов ретранслятора (64).
**Почему.** Проверка 12.11: любой узел мог без ведома получателя залить ему на диск сколько угодно файлов по 64 МиБ (ни
согласия, ни предела числа и суммы), бесплатно спамить сообщениями и вызовами, занять все соединения, всё хранилище соседа
(после чего чужие STORE отвергались) или все маршруты ретранслятора (после чего он никому не строил туннели).
**Компромиссы.** «Знакомый» — тот, кому писали или кто в контактах клиента; знакомому небольшие файлы по-прежнему
приходят без вопроса (как в мессенджерах). Все пределы — на NodeID, а NodeID бесплатен: против Sybil это не защита,
только повышение цены. Учёта трафика ретранслятора по инициатору нет. Предел на loopback по адресу не действует (стенд).
Отправитель ждёт согласия до 135 с — `/api/send_file` держит запрос всё это время.
**Проверка.** `tests/test_file_consent.rs` (6: квота места, одновременные приёмы, ждущие предложения и их тайм-аут,
незнакомец ждёт согласия — отказ доходит до отправителя, принятие — файл доставлен, знакомому — без вопроса; квоты DHT и
маршрутов), `ratelimit::tests`. На эмуляторе: уведомление «предлагает файл» с «Принять / Отклонить», отказ из
уведомления доходит до ПК.

## ADR-46 · Хранилище принятых файлов по собеседникам, файлы больше 2 ГиБ ✅
**Решение.** Принятый файл ложится в `downloads/<первые 16 hex NodeID отправителя>/`, файл больше 2 ГиБ — в подпапку
«Большие файлы» и только после согласия с отдельным предупреждением (⚠, размер, куда ляжет). Предел одного файла —
8 ГиБ (было 64 МиБ). Общая квота 2 ГиБ действует для принимаемых без вопроса; файл, который пользователь принял сам,
ограничен только свободным местом. `GET /api/downloads` — файлы на диске по папкам; клиенты подписывают папку именем
из контактов (Android — «Открыть / Поделиться», desktop — открыть папку в файловом менеджере).
**Почему.** В общей папке файлы разных людей перемешивались, а список передач живёт только в памяти узла — после
перезапуска «где мой файл» было не узнать. Имя папки — по NodeID, а не по имени контакта: имя есть только у клиента,
может меняться и совпадать у двух людей; 16 hex (64 бита) не совпадут случайно.
**Компромиссы.** На диске папки названы шестнадцатеричными префиксами — без приложения их читать неудобно.
Передача больше 2 ГиБ долгая (при 10 МиБ/с — около 4 минут) и не возобновляется после обрыва.
**Проверка.** `tests/test_files.rs::downloads_listed_by_sender_folder`, `test_file_consent.rs` (папка отправителя, «Большие
файлы», квота только для автоматического приёма, размеры); эмулятор: файлы Боба и Кэрол — в разных папках, предложение
3,2 ГиБ от незнакомого узла — с предупреждением.
