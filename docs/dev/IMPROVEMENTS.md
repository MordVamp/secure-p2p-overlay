## 🔵 Концептуальные улучшения (архитектурные альтернативы)

### A1. Bucket refresh — периодическое обновление таблицы маршрутизации
**Что сейчас:** k-bucket обновляется только при входящих сообщениях.  
**Проблема:** Если в диапазоне бакета давно не было сообщений — контакты устаревают незаметно.  
**Стандартный Kademlia:** раз в `refresh_interval` делать lookup случайного ID в диапазоне каждого непустого бакета.  
**Выгода:** Routing table остаётся актуальной, узел не «слепнет» в части адресного пространства.  
**Трудозатраты:** ~2 часа (`tokio::interval` в DhtNode).

### A2. Adaptive α (параллелизм lookup)
**Что сейчас:** α=3 — константа из конфига.  
**Альтернатива:** Уменьшать α при высоком RTT (перегруженная сеть), увеличивать при низком.  
**Выгода:** Лучший баланс между скоростью и нагрузкой.  
**Вывод:** Избыточно для курсовой N=15, но интересно упомянуть на защите.

### A3. Dynamic bucket splitting (классический Kademlia) вместо 256 фиксированных бакетов
**Что сейчас:** 256 фиксированных бакетов (по старшему биту XOR).  
**Оригинальный Kademlia:** один бакет, при заполнении — сплит на два, если диапазон содержит собственный ID.  
**Преимущество:** Более точное распределение при малом N — ближние бакеты заполняются лучше.  
**Недостаток:** Сложнее реализация, нет выигрыша при N=15 (у нас и так достаточно бакетов).  
**Вывод:** Для нашего N=15 фиксированные 256 бакетов — верное решение.

### A4. Connection pool вместо новых TCP-соединений на каждый RPC
**Что сейчас:** `RpcClient::ping()` открывает новое TCP-соединение, делает PING, закрывает.  
**Альтернатива:** Держать пул постоянных соединений к часто используемым узлам.  
**Выгода:** Устранение TCP handshake latency (~10ms) для горячих контактов.  
**Актуальность:** При N=15 на localhost latency незначима. Важно при реальной сети.  
**Трудозатраты:** ~3 часа (DashMap<NodeId, Arc<Mutex<FramedStream>>>).

### A5. Параллельный FIND_NODE с «first K wins» вместо «дождаться α»
**Что сейчас:** Отправляем α=3 запроса, ждём все α ответов перед следующей итерацией.  
**Улучшение:** `tokio::select!` — берём первые K пришедших, остальные отменяем.  
**Выгода:** Lookup быстрее при медленных узлах (slow outlier не блокирует итерацию).  
**Реализация:** `FuturesUnordered` + `take(alpha)`.  
**Трудозатраты:** ~1 час.

### A6. Signed FIND_NODE_RESPONSE (подписанные ответы)
**Что сейчас:** FIND_NODE_RESPONSE не подписан — relay может подменить список контактов.  
**Улучшение:** Ответчик подписывает payload своим Ed25519 ключом, инициатор верифицирует.  
**Выгода:** Защита от active MITM в DHT (Eclipse attack).  
**Актуальность:** Указано в §28 ТЗ как будущее расширение (`NodeRecord`).  
**Трудозатраты:** ~2 часа.

### A7. TTL-aware LRU: выселять контакты старше `session_id_ttl_seconds`
**Что сейчас:** Контакт в бакете живёт вечно, пока бакет не заполнится.  
**Улучшение:** Периодически (bucket refresh) проверять `last_verified_ms` — если > TTL без ответа, убирать.  
**Выгода:** Таблица маршрутизации содержит только «живые» контакты.  
**Реализация:** В рамках A1 (bucket refresh) бесплатно.

### A8. Отдельный binary для оркестратора (`cargo run --bin orchestrator`)
**Что сейчас:** `orchestrator.rs` — заглушка в корне `src/`.  
**Улучшение:** Отдельный бинарник, который поднимает N in-process DhtNode, запускает сценарий, собирает CSV.  
**Выгода:** Воспроизводимый эксперимент без Docker и bash.  
**Трудозатраты:** ~4 часа.
