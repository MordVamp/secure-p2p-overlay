# Гайд к защите: что показать и как

> Доклад — [Doklad.md](Doklad.md) и [Presentation.pptx](Presentation.pptx) (20 слайдов). Теория для вопросов —
> [Theory.md](Theory.md). Здесь — подготовка стенда, сценарий живого показа на ПК и телефоне с командами, запасные
> планы и вопросы. Все команды — из корня репозитория.

## 0. План на защиту (≈ 20 мин)

| Время | Что | Где |
|---|---|---|
| 9–15 мин | доклад; если времени мало — короткая версия (слайды 1–11 и 20, 12–19 — по фразе) | презентация |
| 5–7 мин | живой показ: сеть, переписка, отказ ретранслятора, телефон, звонок | §3–§5 |
| 1–2 мин | доказательства: тесты, захват трафика, сохранённые результаты | §6 |
| остальное | вопросы | §8 |

Главное правило: **всё, что показывается вживую, должно быть поднято до начала доклада** (сеть сходится несколько
секунд, сборка — минуты). Вживую делаются только действия: отправить, убить(программу или процесс:> ), позвонить.

## 1. За день до защиты

```bash
# 1. Сборка (release — быстрее и как в измерениях)
cargo build --release --bins
cargo build --release -p p2p-desktop

# 2. Тесты: убедиться, что всё зелёное (≈ несколько минут); вывод сохранить — показывать его, а не ждать
cargo test --release 2>&1 | tee /tmp/defense_tests.txt | grep "test result"
#   ожидается: 197 тестов, 0 failed (последний сохранённый прогон —
#   experiments/results/08_negative_crypto/20261112_194140_release/cargo_test.txt)

# 3. APK под телефон (если меняли код узла или приложения)
android/build_node.sh release arm64-v8a
(cd android && ./gradlew assembleRelease)
~/Android/Sdk/platform-tools/adb install -r android/app/build/outputs/apk/release/app-arm64-v8a-release.apk
```

- Телефон: зарядить, включить «Не беспокоить», убрать лишние уведомления, тема — светлая или «Ночь в замке».
- Проверить весь сценарий §3–§5 **на той сети, где будет защита** (или на своей точке доступа — см. §7).
- Если показываете экран телефона на проекторе: `sudo pacman -S scrcpy`, затем `scrcpy` при подключённом по USB
  телефоне (отладка по USB включена). Без scrcpy — показывать телефон в руке и дублировать на ПК.
- Открыть заранее вкладки: презентация, этот файл, `experiments/results/` в файловом менеджере, Wireshark (§6).

## 2. За 15 минут до начала

```bash
# Ничего лишнего от прошлых запусков (только по имени процесса, не -f!)
pkill -x p2p-node; pkill -x p2p-desktop; pkill -x p2p-orchestrator

# Стенд А: оркестратор с веб-панелью
./target/release/p2p-orchestrator --gui-port 8080 &
#   браузер: http://127.0.0.1:8080/ → «Запустить узлов: 10» → «Запустить» (порты 7100–7109, панели узлов — 8100–8109)
```

Затем два окна приложения (стенд А, только этот компьютер):

```bash
./target/release/p2p-desktop --profile alice &
./target/release/p2p-desktop --profile bob &
```

| ⚙ Подключение | alice | bob |
|---|---|---|
| Порт узла / API | 7610 / 7695 | 7611 / 7696 |
| Bootstrap-пиры | `127.0.0.1:7100` | `127.0.0.1:7100` |
| Локальная сеть | выкл | выкл |
| Ретрансляторы | 0 | 0 |

«▶ Запустить узел» в обоих → индикатор зелёный → «Контакты и профиль» → опубликовать `alice` / `bob`
(если имя «занято» — запись прошлого запуска ещё жива, подождите 3 мин или возьмите другое имя). В alice открыть чат
`@bob` и отправить «проверка» — чтобы туннель и ключи уже были (второе сообщение пойдёт по установленной сессии).

> Если при первом запуске desktop всплывает окно KWallet / GNOME Keyring — это KEK для ключа узла (ADR-47); открыть
> кошелёк заранее. Для чистого показа без кошелька: `P2P_NO_KEYRING=1 ./target/release/p2p-desktop --profile alice`
> (ключ ляжет в файл 0600).

Стенд Б (телефон) поднимать **отдельным профилем**, не связанным со стендом А: узлы оркестратора анонсируют
`127.0.0.1`, телефон до них не достучится — см. §4.

## 3. Показ на ПК (стенд А)

### 3.1. Сеть распределённая — никто не знает всех (слайды 1, 5, 7)
- Оркестратор (http://127.0.0.1:8080/) → панель любого узла → таблица маршрутизации: контактов меньше, чем N − 1.
- Desktop → 🌐 **Сеть**: контакты, бакеты, записи DHT, время bootstrap; инструмент **FIND_NODE** к NodeID, которого
  нет в таблице, — видны итерации и число запросов.
- Сказать: «узел знает часть сети, а находит любой узел за 2–3 итерации».

### 3.2. Сообщение через туннель (слайды 4, 6, 9)
- alice → чат `@bob` → отправить «привет со стенда». Появляется ✔✔ и RTT: это **подписанное подтверждение
  получателя** (APP_ACK), а не «отправлено». Наведите на сообщение — разбивка: поиск, построение туннеля, проход.
- Кнопка **Маршрут**: `Вы → relay → relay → bob`, у ретрансляторов видны адреса `127.0.0.1:71xx`.
- **Номер безопасности** в alice и bob — одинаковый; отметить «сверен» (слайд 17).
- Из терминала то же самое (для любопытных):
  ```bash
  curl -s 'http://127.0.0.1:7695/api/route?target=@bob' | jq '.tunnel.hops[] | {index, addr, alive}'
  curl -s -X POST 'http://127.0.0.1:7695/api/send' --data-urlencode 'target=@bob' --data-urlencode 'text=из curl' | jq
  ```

### 3.3. Отказ ретранслятора — главный сценарий (слайд 10)
1. В «Маршруте» запомнить порт первого ретранслятора, например `7104`.
2. Оркестратор → у узла 7104 «Стоп» (или в терминале: `kill $(ss -ltnpH 'sport = :7104' | grep -o 'pid=[0-9]*' | cut -d= -f2)`).
3. Отправить ещё одно сообщение из alice → ✔✔ **в той же отправке**; «Маршрут» — новая цепочка без 7104.
- Сказать: «отказ обнаружен по отсутствию сквозного подтверждения, новый туннель построен за ~10 мс, в 10 из 10
  экспериментов — без единой потерянной отправки».

### 3.4. Файл с согласием (слайд 14)
- bob → 🗀 Файлы → отправить alice любой PDF (перетащить в окно). У alice файл приходит **сам** (bob — знакомый,
  < 16 МиБ), SHA-256 ✓, лежит в папке собеседника — кнопка «🗀 bob».
- Чтобы показать вопрос: alice → «Контакты и профиль» → «Приём файлов» → согласие **ask** → отправить ещё раз →
  в строке передачи «Принять / Отклонить» и причина. Вернуть **known**.

### 3.5. Звонок на ПК (слайд 13) — если есть микрофон/колонки
- alice → 📞 Звонки → позвонить bob; в окне bob — полоса «Ответить». Видны MOS, задержка «рот — ухо», потери.
- На одной машине оба окна слышат один микрофон — может быть эхо: выключить микрофон у одной стороны или показать
  звонок с телефоном (§4.3).

### 3.6. Темы — 10 секунд для настроения
«Контакты и профиль» → «Оформление» → «Ночь в замке» / «Цветочная фея». Сказать: темы — не перекраска, а
отрисованные элементы (луна, замок, лепестки).

## 4. Показ с телефоном (стенд Б)

Телефон — полноправный узел (тот же `p2p-node` под ARM). Туннелю нужно ≥ 2 ретранслятора, а в сети «ПК + телефон»
их нет, поэтому desktop запускает 3 вспомогательных узла рядом.

### 4.1. Подготовка ПК
```bash
./target/release/p2p-desktop --profile pc &
```
| ⚙ Подключение (профиль pc) | значение |
|---|---|
| Порт узла / API | 7650 / 7697 (вспомогательные — 7651–7653) |
| Bootstrap-пиры | **пусто** (не подключать к стенду А) |
| Локальная сеть | **вкл** — узел анонсирует LAN-адрес (`--advertise auto`) |
| Ретрансляторы | **3** |

Открыть порты в межсетевом экране (если ufw включён):
```bash
sudo ufw status                        # inactive — ничего делать не нужно
sudo ufw allow 7650:7653/tcp           # после защиты: sudo ufw delete allow 7650:7653/tcp
ip -4 addr | grep inet                 # адрес ПК в Wi-Fi — его покажет и QR
```

### 4.2. Подключение телефона
1. Телефон и ПК в **одной** Wi-Fi-сети (университетский Wi-Fi часто изолирует клиентов — см. §7).
2. Приложение → «Узел» → «Подключиться к компьютеру» → **«Сканировать QR»** → навести на карточку «Подключить телефон» в desktop → «Подключить».
3. Через несколько секунд в заголовке: «в сети · 4 пира». Вкладка «Сеть» на телефоне — пиры и таблица Kademlia.

### 4.3. Что показать
- **Сообщение** ПК → телефон и обратно: ✔✔ и «прочитано»; «Маршрут» в меню чата — цепочка через ретрансляторы ПК.
- **Фото с камеры** телефона → ПК (📎 → камера): приходит с превью, SHA-256 ✓.
- **Звонок** ПК → телефон: на телефоне — полноэкранный вызов; ответить; говорить в телефон — слышно на ПК. Видны MOS
  и задержка. Это лучший «живой» момент: звук идёт через 2 ретранслятора с E2E-шифрованием.
- **Офлайн-доставка**: на телефоне «Узел» → «Остановить»; с ПК отправить сообщение → статус 🕓 «в почтовом ящике»;
  запустить узел на телефоне → через ~10 с сообщение пришло, у ПК ✔✔.
- **Файл от незнакомого** (по желанию): вопрос «Принять / Отклонить» на телефоне с причиной.

### 4.4. Если нет телефона — эмулятор
```bash
~/Android/Sdk/emulator/emulator -avd p2p35 &
~/Android/Sdk/platform-tools/adb install -r android/app/build/outputs/apk/release/app-x86_64-release.apk
~/Android/Sdk/platform-tools/adb forward tcp:7700 tcp:7700   # P2P-порт приложения
```
В эмуляторе «Доступен в локальной сети» — **выкл** (он за NAT, ПК заходит на него через проброс); QR заменяет ссылка
`p2p-overlay://…` из карточки desktop (скопировать и вставить в «Узел» → «Подключиться к компьютеру» → поле «или ссылка p2p-overlay://…»). Если эмулятор пишет
«System UI isn't responding» — «Wait».

## 5. Безопасность — показать, а не рассказать

| Утверждение | Как показать | Время |
|---|---|---|
| Открытого текста в трафике нет | Wireshark на `lo`, фильтр `tcp.port >= 7100 && tcp.port <= 7120`; отправить слово «ВАЛЕНОК»; Edit → Find Packet → String «ВАЛЕНОК» (кодировка UTF-8) — **не найдено** | 1 мин |
| Подмена отвергается | `cargo test --release --test test_tls --test test_e2e --test test_loops --test test_dht_records` | 30 с |
| История на диске зашифрована | `head -c 200 ~/.local/share/p2p-overlay-desktop/alice/node/history.jsonl` → строки `enc1:…` | 10 с |
| Права | `stat -c '%a %n' ~/.local/share/p2p-overlay-desktop/alice/node ~/.local/share/p2p-overlay-desktop/alice/node/*` → 700 / 600 | 10 с |
| Ошибки без адресов | `cargo test --release --test test_peer_errors -- --nocapture 2>&1 \| grep generic:` | 20 с |

Захват без Wireshark (нужны права на `dumpcap` — группа `wireshark`):
```bash
./target/release/p2p-orchestrator scenario pcap       # сценарий сам ищет открытый текст в захвате
```

## 7. Что может пойти не так

| Симптом | Причина | Что делать |
|---|---|---|
| Телефон «в сети · 0 пиров» | изоляция клиентов Wi-Fi в аудитории; межсетевой экран | раздать Wi-Fi **с телефона** и подключить к нему ноутбук (или точку доступа с ноутбука); `sudo ufw allow 7650:7653/tcp` |
| `Not enough relay candidates` | в сети < 4 узлов или ещё не сошлась | подождать 5 с; на ПК «Ретрансляторы» = 3 |
| `@bob` не находится | псевдоним не опубликован / истёк | «Контакты и профиль» → опубликовать снова; или NodeID (кнопка копирования) |
| «псевдоним уже занят» | запись прошлого запуска жива 180 с | подождать или другое имя |
| `Address already in use` | узел от прошлого запуска | `pkill -x p2p-node` |
| Нет звука в звонке на ПК | устройство по умолчанию / эхо двух окон | выбрать устройство в системе; звонить телефону |
| Окно KWallet | KEK в хранилище секретов | открыть кошелёк заранее или `P2P_NO_KEYRING=1` |
| Сеть ведёт себя странно | старые каталоги состояния | закрыть всё, `pkill -x p2p-node`, перезапустить оркестратор |

Если живой показ не удался за 1 минуту — не чинить на глазах у комиссии: «покажу сохранённый прогон» → §6.

## 8. Вопросы и короткие ответы

**Сеть и DHT**
- *Почему Kademlia?* Симметричная XOR-метрика — таблица пополняется из входящих запросов, стабилизация не нужна;
  параллельный поиск (α = 3) не ждёт мёртвых узлов. Слайд 3.
- *Почему k = 3?* Требование упрощённого уровня и N = 15: при большем k таблица почти полная и поиск вырождается в
  прямой запрос (критерий невырождения ТЗ §27).
- *Что если упадёт seed?* Он нужен только при первом входе; дальше узлы знают друг друга; повтор bootstrap (ADR-42).
- *Как запись переживает отказ хранителей?* R = 3 реплики, кворум 2, переопубликование каждые 80 с. Слайд 8.

**Туннели**
- *Что значит «доставлено»?* Подписанный APP_ACK от получателя, а не ответ ретранслятора. Ретранслятор подтверждает
  кадр только после подтверждения следующего узла.
- *Почему нет прямой отправки при отказе?* Это раскрыло бы адресата; туннель перестраивается в той же отправке.
- *Это анонимность как в Tor?* Нет: ретранслятор знает инициатора (строит туннель напрямую), метаданные видны.
  Не заявляется (слайд 11).

**Криптография**
- *Зачем свой AKE, если есть TLS?* ТЗ §11.3; показать понимание рукопожатия; в release не медленнее TLS (25 / 26 мс).
- *Почему самоподписанный сертификат не дыра?* NodeID = хеш ключа сертификата; узел проверяет, что ключ даёт
  ожидаемый NodeID — доверие к привязке, а не к УЦ.
- *Защита от повтора?* В канале — TLS/AKE; в приложении — окно по подписанной метке времени + уже принятые message_id.
- *Есть ли прямая секретность?* В канале и звонках — да; в E2E-конверте — только у отправителя. План — слайд 19,
  Theory §9.
- *Почему ключ узла не меняется?* Подбор ≈ 2¹²⁸, возраст ключа не помогает; от кражи спасает отзыв, а не расписание.
  Раз в год меняется ключ данных истории — в сети не видно. Theory §10.
- *Квантовый компьютер?* Шор ломает X25519 и Ed25519; опасно «записать сейчас — расшифровать потом» для конвертов.
  ML-KEM — только гибрид, минусы — размер ×6, публикация ключа, нет в rustls+ring. Theory §11.

**Атаки**
- *Sybil / Eclipse?* NodeID бесплатен — пределы «на узел» обходятся. Не заявляется; варианты: PoW для NodeID,
  непересекающиеся пути (S/Kademlia). Слайд 15.
- *Может ли кто-то залить мне гигабайты?* Нет: сначала предложение, без согласия на диск не пишется; квоты. Слайд 14.
- *Зачем 64 соединения с адреса?* Иначе одна машина занимает все 1024; до рукопожатия NodeID неизвестен. Цена —
  общий NAT.
- *Можно ли выдать себя за собеседника?* Без его закрытого ключа — нет. Псевдоним можно занять, если владелец
  выключен > 3 мин, — уже добавленные контакты хранятся по NodeID; проверка — номер безопасности.

**Приложения и звонки**
- *Телефон — просто клиент?* Нет, тот же узел на Rust в foreground-сервисе; может быть ретранслятором (режим
  «Эконом» — отключает).
- *Почему не WebRTC?* WebRTC идёт напрямую, мимо оверлея. Звук — по туннелю, без подтверждений.
- *Можно ли доверять задержке 68 мс на одной машине?* Это нижняя граница: нет сетевой задержки. Состав — буфер
  (≈ 40 мс) + кадр + кодек + проход; в реальной сети добавится RTT/2 на каждом переходе. MOS — по E-модели с
  допущением Ie для Opus.
- *Что если потерять хранилище секретов (переустановка)?* Ключ узла и история не расшифруются — нужен экспорт ключа
  с паролем (не сделан, названо в SECURITY_IMPROVEMENTS).

**Эксперимент**
- *Почему одна машина?* Воспроизводимость и изоляция факторов; абсолютные задержки не переносятся — сказано на
  слайде 11. Netem-сценарий (`experiments/scenarios/10_netem.sh`) требует root.
- *Откуда числа?* Каждый слайд подписан каталогом результатов; графики строятся из CSV командой
  `p2p-orchestrator plot`.
