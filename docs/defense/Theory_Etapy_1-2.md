## Часть 0. Что мы реализовали и зачем

### Большая цель проекта

Мы создаём **узел децентрализованной защищённой сети** — программу, которая:

- умеет **находить других участников** без центрального сервера
- умеет **хранить и получать данные** распределённо
- умеет **безопасно общаться** через зашифрованные туннели

Это фундамент для систем типа BitTorrent, I2P или Tor — только мы строим свой стек с нуля на Rust.

### Что такое «оверлейная сеть»

Представь, что обычный интернет — это дороги. **Оверлейная сеть** — это маршруты, которые мы прокладываем **поверх** этих дорог сами. Каждый участник нашей сети знает только несколько соседей, но через них может добраться до любого другого участника.

```
Физическая сеть (интернет):          Наша оверлейная сеть:
A ─────────────── B                  A ←→ C ←→ E
│                 │                  ↑         ↑
│                 │      →→→         │         │
C ─────────────── D                  B ←→ D ←→ F
```

В физической сети все напрямую связаны. В оверлее каждый знает только избранных соседей, но итеративно добирается до любого.

### Что реализовали на Этапах 1–2 (и зачем каждая часть)

| Компонент | Зачем нужен |
|-----------|-------------|
| **TCP-транспорт + кадрирование** | Чтобы узлы вообще могли говорить друг с другом. TCP — это «трубопровод» байтов, кадрирование — способ различать «конец одного сообщения — начало следующего». Без этого узлы не смогли бы разобрать входящий поток |
| **Идентичность (Ed25519 + NodeID)** | Каждый узел должен быть **уникально опознаваем** и **невозможно подделать**. Если нет криптографической идентичности — злоумышленник притворяется кем угодно |
| **Таблица маршрутизации (k-bucket)** | Чтобы знать, **к кому обращаться** при поиске. Это адресная книга узла — ограниченная, умная, самообслуживающаяся |
| **XOR-метрика** | Математический способ измерить «близость» двух узлов в адресном пространстве. Без неё нельзя понять, кто «ближе» к цели |
| **Итеративный lookup** | Алгоритм поиска узла или данных в сети. Без него узел мог бы найти цель только если знает её напрямую — это не масштабируется |
| **Bootstrap** | Механизм **первого вхождения** нового узла в сеть. Без него новый узел изолирован |

## Часть 1. Этап 1 — Транспорт и кадрирование

### 1.1. Проблема: TCP — потоковый протокол

TCP (Transmission Control Protocol) — это «труба» для байтов. Он **гарантирует доставку** и **порядок**, но **не знает о границах сообщений**.

Пример проблемы:

```
Отправитель пишет два сообщения:
  Сообщение A: "PING [32 байта]"
  Сообщение B: "FIND_NODE [45 байт]"

Получатель читает из TCP и получает... неизвестно что:
  Вариант 1: Сначала 10 байт, потом 67 байт
  Вариант 2: Все 77 байт сразу
  Вариант 3: По 1 байту (крайний случай)
```

TCP может **склеить** два сообщения в одно чтение или **разрезать** одно сообщение на несколько. Это называется **TCP framing problem**.

> **Термин: Framing (кадрирование)** — добавление в протокол информации о том, где начинается и заканчивается каждое сообщение.

### 1.2. Решение: фиксированный заголовок + длина payload

Мы добавляем к каждому сообщению **фиксированный 24-байтовый заголовок**, в котором указана длина тела:

```
┌────────────────────────────────────────────────────────────────────┐
│                    КАДР (FRAME)                                    │
├────────────────────────────────────────────────────────────────────┤
│ ЗАГОЛОВОК (всегда ровно 24 байта)                                  │
│  ┌────────┬────────┬──────────────┬────────────────────┬─────────┐ │
│  │version │  type  │    flags     │    request_id      │pay_len  │ │
│  │  1 B   │  1 B   │    2 B       │      16 B          │  4 B    │ │
│  └────────┴────────┴──────────────┴────────────────────┴─────────┘ │
├────────────────────────────────────────────────────────────────────┤
│ ТЕЛО (payload) — ровно pay_len байт, максимум 65 536               │
│  MessagePack-данные сообщения                                      │
└────────────────────────────────────────────────────────────────────┘
```

Алгоритм чтения (`FrameReader`):
1. Читаем байты в буфер (`BytesMut`)
2. Когда в буфере ≥24 байт — читаем заголовок, извлекаем `pay_len`
3. Если `pay_len > 65536` — **ошибка**, закрываем соединение
4. Когда в буфере ≥ 24+pay_len байт — вырезаем готовый кадр
5. Остаток в буфере — начало следующего кадра

> **Почему проверяем длину ДО выделения буфера?** Если сначала выделить `buf.reserve(pay_len)`, злоумышленник может прислать `pay_len = 4 294 967 295` (4 ГБ) и вызвать `OutOfMemoryError`. Это называется **атака на исчерпание памяти** (Memory Exhaustion Attack).

### 1.3. Поля заголовка — каждое по своей роли

#### `version` (1 байт)
Версия протокола. Сейчас всегда `1`. Зачем:
- Если в будущем изменим формат кадра — изменим версию
- Старые узлы увидят `version=2` и откажутся (вместо молчаливого неправильного разбора)
- ТЗ §7: при несовпадении версии — закрыть соединение + ERROR

#### `type` (1 байт)
Тип сообщения — число от 0x01 до 0x7F. Определяет, **что делать с payload**.

```
0x01 = PING          — проверить, жив ли узел
0x02 = PONG          — ответ на PING
0x03 = FIND_NODE_REQUEST  — найди мне K ближайших к этому ID
0x04 = FIND_NODE_RESPONSE — вот они
0x7F = ERROR         — что-то пошло не так
```

Заметь: `ERROR = 0x7F`, не `0xFF`. `0xFF` — зарезервировано на будущее, его нельзя самовольно занять (§8 ТЗ).

#### `flags` (2 байта)
Битовые флаги:
- `IS_RESPONSE = 0x0001` — этот кадр является **ответом** на запрос
- `IS_ERROR = 0x0002` — это ответ-ошибка
- `MORE_FRAGS = 0x0004` — зарезервировано для фрагментации (не используется в Этапах 1–2)

На Этапах 1–2 `flags` всегда `0x0000` в запросах и `0x0001` в ответах.

#### `request_id` (16 байт = UUID)
Это **уникальный идентификатор запроса**. Генерируется через CSPRNG (криптографически стойкий генератор случайных чисел).

Зачем:
1. **Корреляция ответа с запросом**: когда придёт PONG, мы знаем, на какой PING он отвечает
2. **Дедупликация**: если пакет пришёл дважды — `request_id` одинаковый, игнорируем повтор

> **Термин: UUID** — Universally Unique Identifier. 128-битное число, вероятность коллизии ≈ 0. Мы используем UUID v4 (случайный).

> **Термин: CSPRNG** — Cryptographically Secure Pseudo-Random Number Generator. Генератор, который нельзя предсказать даже зная предыдущие значения. В Rust: `rand::rngs::OsRng`.

#### `payload_length` (4 байта, big-endian)
Длина тела в байтах. Максимум: `65 536 = 64 КБ = MAX_FRAME_PAYLOAD`.

> **Термин: Big-endian** — порядок байт, при котором **старший** байт идёт первым. Например, число `0x00010203` записывается как байты `00 01 02 03`. Альтернатива — little-endian (младший байт первым). В сетевых протоколах принят big-endian — «сетевой порядок байт».

### 1.4. Сериализация payload: MessagePack

Данные внутри кадра сериализованы в **MessagePack** — бинарный формат.

Зачем не JSON?

| Критерий | JSON | MessagePack |
|----------|------|-------------|
| NodeID (32 байта) | base64 → **44 байта** | raw bytes → **33 байта** |
| Скорость парсинга | умеренная | в 2–5× быстрее |
| Человекочитаемость | ✅ | ❌ (нужен hex-дамп) |
| Небезопасная десериализация объектов | нет | нет |
| Схема данных | нет | нет (но есть в нашем коде) |

> **Термин: Сериализация** — преобразование структуры данных в байты для передачи по сети. **Десериализация** — обратное преобразование.

> **Небезопасная десериализация** — когда формат данных позволяет выполнить произвольный код при разборе (уязвимость Java, Python pickle). MessagePack и JSON этого не допускают.

### 1.5. Обработка ошибок протокола (§10 ТЗ)

При любом нарушении протокола узел должен:
1. Отправить ERROR-кадр (если возможно)
2. Закрыть соединение
3. **Не падать** — другие соединения продолжают работать

```
Нарушения → закрыть соединение:
  • неизвестная версия протокола
  • payload_length > MAX_FRAME_PAYLOAD
  • невозможно декодировать payload
  • payload не соответствует схеме типа
  • неверная корреляция request_id
  • TCP разрыв до получения полного кадра
```

> **Термин: Fault isolation** — изоляция отказов. Ошибка одного соединения не должна убивать весь процесс. В нашем коде каждое соединение обрабатывается в отдельном `tokio::spawn`.

### 1.6. Диспетчер (§11 ТЗ)

После успешного разбора кадра — **транспортный уровень** передаёт его **диспетчеру**. Диспетчер выбирает обработчик только по `type` и **не знает ничего о Kademlia**.

```
TCP байты
    ↓
FrameReader (кадрирование)
    ↓
Frame { version, type, flags, request_id, payload }
    ↓
RpcHandler::handle(frame) → match frame.msg_type { ... }
    ↓                              ↓
handle_ping(frame)         handle_find_node(frame)
```

Это принцип **разделения ответственности** (Separation of Concerns): транспорт не знает о логике, логика не знает о байтах.

## Часть 2. Этап 2 — Идентичность и DHT

### 2.1. Зачем нужна криптографическая идентичность

В нашей сети нет центрального регистра пользователей. Как тогда убедиться, что узел — тот, за кого себя выдаёт?

**Ответ**: криптографическая пара ключей. Узел генерирует:
- `private_key` (секретный ключ) — только у него, никому не передаётся
- `public_key` (открытый ключ) — можно раздать всем

Всё, что подписано `private_key`, может проверить любой знающий `public_key`.

> **Термин: Асимметричная криптография** — система, где для шифрования и дешифрования используются **разные** ключи. Подписал приватным — проверяют публичным.

### 2.2. Ed25519 — наша схема подписи

**Ed25519** — алгоритм цифровой подписи на основе эллиптической кривой **Curve25519**.

Ключевые свойства:
- Ключ: **32 байта** (vs 256–512 байт у RSA-2048)
- Подпись: **64 байта**
- Верификация: ~**190 000** подписей/сек
- **Детерминированная**: одинаковые данные + ключ → одинаковая подпись (не нужен random nonce)
- **Безопасность**: ~128 бит (сопоставима с AES-128)

> **Термин: Эллиптическая кривая** — математический объект над конечным полем. Операции на ней быстрые и криптографически стойкие при малых размерах ключей.

> **Термин: Цифровая подпись** — способ доказать, что данные созданы владельцем private key. Верификация: `verify(public_key, data, signature) → true/false`.

### 2.3. NodeID — криптографическая идентичность в адресном пространстве DHT

```
NodeID = SHA-256(0x01 ‖ public_key_bytes)
         ↑              ↑
    хеш-функция    контекстный домен (байт 0x01 = "это Ed25519 ключ")
```

Зачем хеш, а не сам pubkey?

1. **Фиксированный размер**: pubkey может быть разного размера для разных алгоритмов. SHA-256 всегда даёт 32 байта.
2. **Равномерное распределение**: SHA-256 выдаёт псевдослучайные числа — NodeID равномерно распределены в пространстве `[0, 2^256)`. Это критично для DHT.
3. **Нельзя выбрать произвольный ID**: чтобы получить конкретный NodeID, нужно найти pubkey с нужным SHA-256 — это вычислительно невозможно (birthday attack: 2^128 попыток).

> **Термин: SHA-256** — криптографическая хеш-функция. Принимает данные любого размера, возвращает 32 байта. Свойства: необратима, нельзя найти коллизию.

> **Термин: Контекстный домен** — байт-префикс `0x01`, отделяющий использование ключа в разных контекстах. Если бы завтра добавили ECDSA ключи (`0x02 ‖ key`), NodeID не пересеклись бы даже при одинаковом бинарном представлении ключа.

> **Термин: Sybil-атака** — злоумышленник создаёт множество «фиктивных» узлов с подобранными ID, чтобы контролировать часть DHT. NodeID = SHA-256(pubkey) делает это вычислительно невозможным — нельзя подобрать ключ под нужный ID.

### 2.4. DHT — Distributed Hash Table

**Распределённая хеш-таблица** — это способ хранить пары `(key → value)` **без центрального сервера**, распределив ответственность между узлами.

Аналогия: словарь разрезан на части, каждый узел хранит страницы, «близкие» к его NodeID.

```
Обычная хеш-таблица (централизованная):    DHT (Kademlia):
┌─────────────────────────────────────┐     Node A знает → ключи рядом с ID_A
│ Сервер                              │     Node B знает → ключи рядом с ID_B
│  key_1 → value_1                    │     Node C знает → ключи рядом с ID_C
│  key_2 → value_2                    │
│  key_N → value_N                    │     STORE: найди K ближайших к key → сохрани
└─────────────────────────────────────┘     FIND_VALUE: найди K ближайших к key → спроси
```

На Этапах 1–2 мы реализуем только **поиск узлов** (FIND_NODE). Хранение значений (STORE/FIND_VALUE) — Этап 4 (у нас уже реализован).

### 2.5. XOR-метрика — «расстояние» в пространстве NodeID

**XOR-расстояние** между двумя ID:
```
distance(A, B) = A XOR B    (побитовое исключающее ИЛИ)
```

Пример:
```
A = 0101 1100
B = 0110 0011
-----------
d = 0011 1111   →  расстояние = 63

A = 0101 1100
C = 0101 1101
-----------
d = 0000 0001   →  расстояние = 1  (C «ближе» к A, чем B)
```

Свойства XOR-метрики, которые делают её идеальной для DHT:
1. `d(A, A) = 0` — расстояние до себя = 0
2. `d(A, B) = d(B, A)` — симметрия (важно для двусторонней маршрутизации)
3. `d(A, C) ≤ d(A, B) XOR d(B, C)` — неравенство треугольника
4. **Детерминированность**: для каждой пары (A, target) всегда один и тот же набор K ближайших — алгоритм сходится
5. **Без географии**: «ближайшие» узлы в XOR-пространстве могут быть физически далеко

> **Термин: Метрика** — функция расстояния, удовлетворяющая аксиомам: d(A,A)=0, d(A,B)=d(B,A), d(A,C) ≤ d(A,B)+d(B,C). XOR — корректная метрика.

> **Термин: Адресное пространство** — множество всех возможных NodeID: числа от 0 до 2^256 - 1. NodeID равномерно распределены в нём.

### 2.6. K-bucket — структура данных таблицы маршрутизации

Каждый узел не может знать всех участников сети (N=13–15, но могло быть миллиард). Поэтому он хранит только **K избранных соседей** в каждом «диапазоне расстояний».

#### Как устроен один k-bucket

```
Bucket[i] содержит узлы, у которых:
  2^i ≤ XOR-distance(own_id, contact_id) < 2^(i+1)

Bucket[0]:  расстояние 1  (самые близкие)
Bucket[1]:  расстояние 2-3
Bucket[2]:  расстояние 4-7
...
Bucket[255]: расстояние 2^255 .. 2^256-1  (самые далёкие)
```

У нас 256 бакетов — по одному на каждый бит XOR.

#### LRU-порядок внутри бакета

Контакты в бакете упорядочены по времени последнего успешного наблюдения:

```
VecDeque:  [голова (LRU = самый старый)] ← ... → [хвост (MRU = самый свежий)]
```

> **Термин: LRU** — Least Recently Used. «Наименее недавно использованный». Голова очереди — тот, кого давно не видели.

> **Термин: MRU** — Most Recently Used. Хвост — кого видели последним.

#### Правила обновления бакета (§18.2 ТЗ)

Когда приходит сообщение от узла X:

```
1. X уже в бакете?
   ДА → переместить X в хвост (обновить last_seen)
   НЕТ → перейти к п.2

2. Бакет не заполнен (size < K)?
   ДА → добавить X в хвост
   НЕТ → перейти к п.3

3. PING к узлу в голове (LRU):
   Не ответил → удалить его, добавить X в хвост
   Ответил    → его переместить в хвост, X — отклонить
```

**Почему не вытеснять живой LRU?** Долгоживущие узлы статистически надёжнее. Kademlia измерил: узел, проработавший 1 час, с вероятностью 50% проработает ещё 1 час. Новый узел — непроверенный.

#### Защита от конфликтов NodeID (§18.3 ТЗ)

```
Один NodeID = один узел. Если пришёл контакт с:
  - тем же NodeID + другим pubkey → ОТКЛОНИТЬ (нарушение идентичности)
  - тем же NodeID + другим адресом → обновить только после проверки доступности
```

### 2.7. PING — проверка доступности

`PING` — простейшая операция DHT. Используется для:
1. Проверить, что узел жив (при LRU-вытеснении)
2. Объявить о себе при первом контакте
3. Обновить `last_verified_ms` в таблице маршрутизации

Payload:
```json
{
  "sender": { "node_id": "...", "host": "127.0.0.1", "port": 7001, "..." },
  "timestamp_ms": 1727430000123
}
```

Ответ `PONG` содержит:
- **тот же** `request_id` — чтобы инициатор знал, на что отвечают
- `ping_timestamp_ms` — скопировано из PING (для измерения RTT)
- `responder_timestamp_ms` — когда ответили (для диагностики)
- собственный контакт ответчика

> **Термин: RTT** — Round-Trip Time. Время «туда и обратно». RTT = момент_PONG - момент_PING.

### 2.8. FIND_NODE — поиск ближайших соседей

`FIND_NODE_REQUEST` содержит `target_node_id`. Получатель отвечает списком **K ближайших** к target контактов, которых он знает.

Важные условия ответа (§20 ТЗ):
- Не более K контактов (K = K_BUCKET_SIZE = 3)
- Отсортированы по **возрастанию** XOR-расстояния до target
- Не включают самого отвечающего (зачем сообщать о себе — инициатор уже с ним разговаривает)

```json
{
  "responder": { "node_id": "..." },
  "target_node_id": "ff00aa...",
  "contacts": [
    { "node_id": "fe10bb...", ... },   ← ближайший к target
    { "node_id": "fd20cc...", ... }    ← чуть дальше
  ]
}
```

### 2.9. Итеративный lookup — как находим любой узел в сети

Задача: найти контакт с данным `target_id`, не имея его в своей таблице маршрутизации.

**Алгоритм** (параметр: α=3 — параллелизм):

```
Шаг 0: Берём α=3 ближайших к target из СВОЕЙ таблицы

ЦИКЛ:
  Шаг 1: Параллельно отправляем FIND_NODE к α кандидатам
  Шаг 2: Каждый возвращает K ближайших по их мнению
  Шаг 3: Объединяем все ответы в общий список
  Шаг 4: Берём α новых ближайших (которым ещё не спрашивали)
  Шаг 5: Если ближайший не улучшился за раунд → СТОП

РЕЗУЛЬТАТ: K ближайших найденных контактов
```

Визуализация:

```
Инициатор (ID=0x00)  target=0xFF

Итерация 1:
  Знаю: {0x10, 0x20, 0x40}
  Спрашиваю у 0x40: "кто ближе к 0xFF?"
  Получаю: {0xC0, 0xD0, 0xE0}

Итерация 2:
  Знаю: {0x10, 0x20, 0x40, 0xC0, 0xD0, 0xE0}
  Спрашиваю у 0xE0: "кто ближе к 0xFF?"
  Получаю: {0xFF, 0xFE, 0xFD}  ← нашли цель!

Итерация 3: 0xFF ближе 0xE0 → прогресс есть, продолжаем или СТОП
```

**Сложность**: O(log N) итераций при N узлах. При N=15 → ≈4 итерации.

> **Термин: Сходимость алгоритма** — гарантия, что процесс завершится и даст правильный ответ. Итеративный Kademlia сходится, потому что каждый шаг XOR-расстояние до target монотонно убывает или остаётся прежним.

### 2.10. Bootstrap — первое вхождение в сеть

Новый узел не знает никого. Нужен **хотя бы один известный адрес** — bootstrap-узел.

Процедура `join()`:

```
1. PING bootstrap-узла → добавить его в routing table
2. Self-lookup: FIND_NODE(own_id)
      → промежуточные узлы возвращают тех, кто близко к нашему ID
      → мы добавляем их в таблицу
      → попутно объявляем себя всем встреченным
3. Repeat FIND_NODE for other bucket targets (bucket refresh)
```

После join-а узел **независим** от bootstrap-узла. Даже если bootstrap упадёт — узел знает соседей из итеративного lookup и продолжает работать.

#### Схемы bootstrap

**Star (звезда)**: все подключаются к одному seed-узлу
```
    01 (seed)
   /│\
  02 03 04 05
```
Быстро, но seed — единая точка отказа **на старте**.

**Ring (кольцо)**: каждый узел подключается к предыдущему
```
01 → 02 → 03 → 04 → 05
```
Медленнее (O(N) шагов до полного знания), нет SPOF.

### 2.11. Contact — структура описания узла

В сети каждый узел описывается структурой Contact:

```
Contact {
  node_id:            bytes[32]  — криптографический ID
  identity_algorithm: string     — "ed25519"
  identity_public_key: bytes     — открытый ключ для верификации
  host:               string     — IP-адрес
  port:               uint16     — TCP-порт
  last_seen_ms:       uint64     — когда последний раз видели (локально)
  last_verified_ms:   uint64     — когда последний раз подтвердили PING (локально)
}
```

> **Важно:** `last_seen_ms` и `last_verified_ms` — **локальные** метки. Они **не принимаются от удалённого узла** как достоверные — иначе злоумышленник мог бы прислать `last_verified_ms = сейчас` для мёртвого узла.

## Часть 3. Понятия из нашего кода

### `FrameReader` и `ReadItem`

`FrameReader` — конечный автомат с буфером `BytesMut`. Метод `feed(bytes)` возвращает:

```rust
enum ReadItem {
    Frame(Frame),        // полный кадр готов
    NeedMoreData,        // ещё не хватает байт
    Error(FrameError),   // нарушение протокола
}
```

### `RpcHandler` и `RpcClient`

`RpcHandler` — **сервер**: принимает входящие кадры, обрабатывает, возвращает ответ.  
`RpcClient` — **клиент**: формирует исходящий запрос, ждёт ответа (с тайм-аутом).

`PendingRpc` — хранит ожидающие ответа запросы (по `request_id`). При получении ответа — находит нужный `request_id` и доставляет.

### `RoutingTable` и `KBucket`

`RoutingTable` — контейнер из 256 `KBucket`.  
`KBucket` — `VecDeque<Contact>` с ограниченной ёмкостью `capacity = K`.

Метод `find_closest(target, k)` — обходит все бакеты, собирает контакты, сортирует по XOR-расстоянию до target, возвращает первые K.

### `DhtNode::join()`

```
1. Для каждого bootstrap-адреса:
   - создать соединение
   - отправить PING
   - при успехе: добавить в routing table
2. Self-lookup: find_node(own_id)
   - запускает итеративный lookup к себе
   - заполняет ближние бакеты
```

## Часть 4. Почему именно так (архитектурные решения)

| Решение | Альтернатива | Почему выбрали |
|---------|-------------|---------------|
| Rust | Python, Go, Java | Нет GC-пауз, строгие типы исключают целый класс сетевых ошибок, `tokio` — промышленный async runtime |
| MessagePack | JSON, Protobuf | Компактнее для бинарных данных, проще схемы, нет кодогенерации |
| Ed25519 | RSA, ECDSA secp256k1 | Быстрее, меньше ключ, нет random nonce → детерминированность |
| Фиксированные 256 бакетов | Динамическое разбиение | Проще реализация, достаточно для N=13–15 |
| K=3 (упрощённый уровень) | K=4 (продвинутый) | N=15: log₂(15)≈4 бакета → K=3 даёт ≤12 контактов, невырождение выполнено |
| α=3 | α=1 (последовательный) | Параллелизм снижает latency lookup при тех же O(log N) RPC |
| TCP (не UDP) | UDP | На Этапах 1–2 требует ТЗ; надёжная доставка, не нужна своя retransmission |

