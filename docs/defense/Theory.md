## 1. P2P-сети и оверлей

### Что такое оверлейная сеть?
**Оверлейная сеть** — логическая сеть поверх физической (TCP/IP). Узлы общаются через прикладные протоколы, а не напрямую по IP. Пример: BitTorrent, Tor, I2P.

**Преимущества:**
- Децентрализация — нет единой точки отказа
- Анонимность — реальные IP скрыты за узлами-ретрансляторами
- Масштабируемость — маршрутизация без центрального сервера

### Типы P2P-сетей
| Тип | Примеры | Особенность |
|-----|---------|-------------|
| Неструктурированные | Gnutella | Flood-поиск, O(N) трафик |
| Структурированные DHT | Kademlia, Chord | Детерминированный поиск O(log N) |
| Гибридные | BitTorrent | Трекер + DHT |

**Наш проект:** структурированная DHT-сеть на основе Kademlia.

## 2. Kademlia DHT

### Идентификаторы узлов
- **NodeID** = SHA-256(0x01 ‖ Ed25519_pubkey) → 256-битный ID
- Равномерное распределение в пространстве идентификаторов
- Детерминированность: один ключ → один NodeID

### XOR-метрика
Расстояние между узлами: `d(A, B) = A XOR B`

Свойства XOR-метрики:
- `d(A, A) = 0` (узел от самого себя)
- `d(A, B) = d(B, A)` (симметрия)
- `d(A, C) ≤ d(A, B) XOR d(B, C)` (неравенство треугольника)
- Детерминированность: каждый запрос находит те же K ближайших

### K-bucket
Каждый узел делит пространство ID на **256 бакетов** по старшему биту XOR-расстояния.

```
Bucket[i] = контакты, у которых 2^i ≤ XOR-расстояние < 2^(i+1)
```

**LRU-порядок:** голова = самый старый (LRU), хвост = самый свежий.  
При заполнении (K=3) — PING LRU-узла. Если жив — новый отклоняется. Если мёртв — вытесняется.

**Почему LRU а не FIFO?** Kademlia привилегирует долгоживущие узлы — они статистически надёжнее.

### Итеративный lookup
```
1. Начало: α=3 ближайших из локальной таблицы
2. Параллельно: FIND_NODE к α кандидатам
3. Объединить ответы, добавить новых кандидатов
4. Остановка: ближайший не улучшился за раунд
5. Возврат K ближайших найденных
```

Сложность: **O(log N)** RPC-вызовов при N узлах.

### STORE / FIND_VALUE
- `STORE(key, value, ttl)` — сохранить запись на K ближайших к key узлах
- `FIND_VALUE(key)` — если есть → вернуть value; если нет → вернуть K ближайших (как FIND_NODE)
- TTL: записи истекают, периодически republish

## 3. Транспортный протокол

### Кадр (24-байтовый заголовок)
```
Offset  Size  Field           Описание
0       1     version         Версия протокола (= 1)
1       1     msg_type        Тип: PING=0x01, PONG=0x02, FIND_NODE=0x03/04...
2       2     flags           IS_RESPONSE=0x1, IS_ERROR=0x2
4       16    request_id      UUID v4 — сопоставление запрос/ответ
20      4     payload_length  Длина payload (BE, 0..65536)
24      var   payload         MessagePack-данные
```

### Почему не JSON/Protobuf?
**MessagePack:** бинарный формат, компактнее JSON для NodeID (32B → 33B vs 44B base64), быстрее парсинг, нет схемы.

### TCP framing problem
TCP — потоковый протокол, границы сообщений не гарантированы. Возможные ситуации:
- **Partial read:** заголовок пришёл в двух TCP-сегментах
- **Coalescing:** два кадра в одном read()

**Решение:** `FrameReader` — конечный автомат с буфером `BytesMut`:
1. Накапливаем байты до `HEADER_LEN=24`
2. Читаем `payload_length`, проверяем ≤ MAX (защита от OOM)
3. Накапливаем до `HEADER_LEN + payload_length`
4. Возвращаем полный Frame

## 4. Идентичность узла

### Ed25519
- **Схема:** Schnorr-подобная подпись на кривой Curve25519
- **Размер ключа:** 32 байта (pubkey), 64 байта (подпись)
- **Скорость:** ~70k знаков/сек, ~190k верификаций/сек
- **Детерминированность:** одинаковые данные → одинаковая подпись (нет random nonce)

### NodeID из pubkey
```rust
NodeID = SHA-256(0x01 || pubkey_bytes)  // 0x01 = контекстный домен
```

Обеспечивает:
- Уникальность: коллизия SHA-256 → нереальна (birthday: 2^128 попыток)
- Привязку ID к ключу: нельзя выбрать произвольный ID без знания ключа

### Хранение ключей
- Файл: `{STATE_DIR}/identity.key` (права `0600`) или **`identity.key.enc`** — зашифрован ключом KEK из хранилища
  секретов системы (Android Keystore, Secret Service / Keychain / Windows), см. §14
- При рестарте: тот же ID (загружается из файла); каталог состояния — `0700`
- В git: `state/` в `.gitignore` — ключи никогда не попадают в репо

## 5. Безопасность канала

### TLS 1.3 (упрощённый уровень)
- **mTLS:** взаимная аутентификация — оба узла проверяют сертификат другого
- **0-RTT отключён:** нет session tickets → защита от replay между соединениями
- **Self-signed X.509:** сертификат из Ed25519-ключа узла (через `rcgen`)
- **После handshake:** извлечь pubkey peer → пересчитать NodeID → сравнить с заявленным

### Replay-защита (SessionTracker)
- Sliding window: каждый `request_id` (16B UUID) регистрируется при получении
- Повторный `request_id` в окне TTL → отклоняется без прикладного действия
- TTL настраивается в конфиге (default: 3600 с)

### Угрозы и защиты
| Угроза | Защита |
|--------|--------|
| Перехват трафика (passive) | TLS 1.3 шифрование |
| MITM (active) | mTLS — оба проверяют сертификаты |
| Replay-атака | request_id + SessionTracker |
| Sybil-атака (много ID одного узла) | **частично:** NodeID = SHA-256(pubkey) нельзя *выбрать*, но создать много ключей дёшево — см. §13 |
| Подделка подписи сообщения | Ed25519 подпись в AppMessage |

## 6. Туннели

### Зачем туннель?
TLS защищает канал от перехвата, но не скрывает, кто с кем говорит. В туннеле данные идут только через ретрансляторы
(≥ 2), и каждый **пересылает** кадр только предыдущему и следующему узлу; получатель видит последний ретранслятор, а
не отправителя. Честная оговорка: у нас инициатор строит туннель, обращаясь к каждому ретранслятору напрямую, поэтому
ретранслятор знает инициатора — до луковой маршрутизации (Tor) это не дотягивает (SECURITY_IMPROVEMENTS п. 1).

### Машина состояний
```
BUILDING ──→ ACTIVE ──→ DEGRADED ──→ DEAD
    │                       │
    └──────────────────────→┘
         (при ошибке построения)
ACTIVE → CLOSING → DEAD
```

- `BUILDING`: согласование с relay (TUNNEL_BUILD RPC)
- `ACTIVE`: все relay подтвердили, данные идут
- `DEGRADED`: давно (> 60 с) не было сквозного подтверждения — туннелем можно пользоваться, простой ≠ отказ
- `DEAD`: отправка не подтверждена — в той же отправке строится новый туннель без отказавшего узла

### Построение туннеля (упрощённый уровень)
1. Выбрать `min_relays=2` кандидатов из RoutingTable
2. Последовательно TUNNEL_BUILD к каждому → ждём TUNNEL_BUILD_OK
3. При неудаче → 3 попытки с разными кандидатами

## 7. Bootstrap-схемы

### Star
```
node-01 (seed)
  ├── node-02 → bootstrap: node-01
  ├── node-03 → bootstrap: node-01
  ├── node-04 → bootstrap: node-01
  └── node-05 → bootstrap: node-01
```
**Плюс:** быстрая сходимость. **Минус:** seed — SPOF на старте.

### Ring
```
node-01 → node-02 → node-03 → node-04 → node-05 → (node-01)
```
**Плюс:** нет SPOF. **Минус:** медленная сходимость (O(N) шагов до полного знания).

### Процедура join()
1. PING каждого bootstrap-адреса → добавить в RoutingTable
2. Self-lookup: `FIND_NODE(own_id)` — заполнить таблицу маршрутизации
3. Записать в лог итоговый размер таблицы

## 9. Сквозное шифрование и прямая секретность

### Запечатанный конверт (sealed box)
```
отправитель:  (e, E) — одноразовая пара X25519
              shared = X25519(e, R_получателя)            R — выводится из Ed25519-ключа получателя
              K = HKDF-SHA256(salt = E ‖ R, ikm = shared, info = "p2p-e2e-v1")
              конверт = {v=1, to, E, nonce (12 Б), AES-256-GCM(K, nonce, AppMessage с подписью Ed25519,
                                                        aad = "p2p-e2e-v1" ‖ to ‖ E)}
получатель:   shared = X25519(r, E) → тот же k
```
- **AES-256-GCM** — AEAD: шифрует и проверяет целостность (тег 16 Б); любой изменённый бит → отказ.
- Подпись **внутри** конверта (sign-then-encrypt): ретранслятор не видит, кто автор, а получатель точно знает;
  AAD привязывает шифртекст к получателю (`to`) и одноразовому ключу (`E`).
- Одноразовый nonce обязателен: повтор nonce с тем же ключом в GCM раскрывает поток и ломает аутентификацию.

### Прямая секретность (forward secrecy)
**Определение:** утечка долговременного ключа **сегодня** не раскрывает сообщения **вчерашние**. Достигается тем,
что сообщение зашифровано ключом, которого уже не существует.

| Где | Есть ли | Почему |
|---|---|---|
| Канал TLS 1.3 / своё рукопожатие (AKE) | да | одноразовые ключи (ECDHE) на каждое соединение |
| Ключ звонка | да | одноразовые X25519 **обеих** сторон |
| E2E-конверт, сторона отправителя | да | `e` стирается сразу |
| E2E-конверт, сторона получателя | **нет** | `r` — постоянный; кто сохранил конверт (ретранслятор, хранитель почтового ящика) и позже украл ключ — прочитает |

### Как это решают
- **Подписанный сменяемый ключ (signed prekey):** отдельная пара X25519, подписанная ключом личности, публикуется в
  DHT и меняется раз в неделю; старый закрытый ключ стирается → утечка раскрывает ≤ 2 недель.
- **X3DH** (Signal): первое сообщение — несколько обменов DH (ключ личности, предключ, одноразовый ключ) — работает,
  даже когда получатель офлайн.
- **Double Ratchet:** новый ключ на каждое сообщение (KDF-цепочка) + новый DH при каждом ответе → прямая секретность
  для каждого сообщения и **восстановление после взлома** (post-compromise security).

## 10. Срок жизни ключей

### Почему ключ личности не меняют по расписанию
- Найти закрытый ключ Ed25519 по открытому: лучшая атака — **ро-метод Полларда**, ≈ √(2²⁵²) ≈ 2¹²⁶…2¹²⁸ операций над
  точками кривой. При 10¹⁸ оп/с — порядка 10¹³ лет.
- Атакующий может начать подбор в любой момент, как только увидел открытый ключ — **возраст ключа ему не помогает**.
  Плановая смена от подбора не защищает.
- Долгоживущие ключи личности — норма: Signal, основной ключ GnuPG, ключ хоста SSH, ключ личности Tor.

### Что на самом деле требует смены
| Причина | Защита |
|---|---|
| Ключ **украден** незаметно | **отзыв** («этот ключ больше не мой»), а не расписание: укравший подпишет и «переезд» |
| Ключ шифрования используется вечно | короткоживущий ключ шифрования, подписанный ключом личности (§9) |
| Объём данных под одним ключом (AES-GCM: ≤ 2³² сообщений со случайным nonce) | смена **ключа данных** (у нас — ключ истории, §14) |
| Квантовый компьютер | смена алгоритма (§11), а не ключа |

### У нас
- **Ключ узла** (Ed25519) — постоянный; NodeID = SHA-256 ключа, поэтому новый ключ = новый NodeID = другой узел.
- **Ключ данных истории** — меняется (раз в год или вручную); живёт только на устройстве, в сети смена не видна —
  «окна» для подмены нет.

## 11. Постквантовая криптография

### Угроза
- **Алгоритм Шора** на достаточно большом квантовом компьютере решает задачу дискретного логарифма на эллиптических
  кривых за полиномиальное время → ломаются **и X25519, и Ed25519**.
- **Алгоритм Гровера** даёт лишь квадратичное ускорение перебора → AES-256 и SHA-256 остаются стойкими (≈ 2¹²⁸).
- **«Записать сейчас — расшифровать потом»** (harvest now, decrypt later): опасность уже сегодня для
  **конфиденциальности** долго хранимых данных. Для **подписей** — нет: подделать подпись можно только когда
  квантовый компьютер уже есть.

### ML-KEM (FIPS 203, 2024; бывший Kyber)
- Основан на задаче **Module-LWE** (обучение с ошибками на решётках).
- Это **KEM** (механизм инкапсуляции ключа), а не Диффи–Хеллман: `Encaps(pk) → (ct, ss)`, `Decaps(sk, ct) → ss`.
  Ключ получателя нельзя вывести из ключа Ed25519 — его надо публиковать.

| | X25519 | ML-KEM-768 |
|---|---|---|
| открытый ключ | 32 Б | 1184 Б |
| шифротекст / одноразовый ключ | 32 Б | 1088 Б |
| скорость | десятки мкс | десятки мкс |

- **Гибрид:** `ss = HKDF(ss_X25519 ‖ ss_ML-KEM ‖ транскрипт)` — стойко, пока стойка хотя бы одна часть; защищает от
  ошибок в молодых реализациях (KyberSlash, 2023–24 — утечка по времени). Так делают TLS (`X25519MLKEM768`), Signal
  (PQXDH), Chrome, OpenSSH.
- Подписи: **ML-DSA** (FIPS 204) — подпись ≈ 2,4 КБ, ключ ≈ 1,3 КБ.
- **У нас:** не реализовано. Минусы и план — [SECURITY_IMPROVEMENTS](../dev/SECURITY_IMPROVEMENTS.md#почему-ключ-узла-не-меняют-и-нужен-ли-ml-kem-выводы):
  ×6 к размеру короткого сообщения, публикация ключа в DHT, `rustls` + `ring` без ML-KEM; порядок — сначала сменяемый
  ключ (§9), в нём гибрид.

## 12. Доверие к ключам

### Личность и адрес
- **Личность = NodeID** (хеш ключа). **Адрес** (IP:порт) — только местоположение; публикуется подписанной записью
  NodeRecord и может меняться.
- Каждое соединение доказывает владение ключом (TLS-сертификат на ключе узла или подпись в AKE); узел сверяет ключ с
  ожидаемым NodeID — ответ «не того» узла по известному адресу отвергается.

### Как убедиться, что NodeID принадлежит Алисе
| Модель | Как | Где |
|---|---|---|
| **TOFU** (trust on first use) | первому увиденному ключу доверяют, смену — замечают | SSH `known_hosts`, у нас — до сверки |
| **Сверка отпечатка** | номер безопасности = хеш обоих ключей, сравнить лично | Signal, **у нас** |
| **Сеть доверия** (Web of Trust) | ключи подписывают друг другу на **keysigning party**, доверие транзитивно | GnuPG, Debian |
| **PKI** | удостоверяющий центр подписывает сертификат | HTTPS |

### Псевдонимы
- Подписанная запись DHT «имя → NodeID»; **кто первым записал, того и имя**, пока запись жива (TTL 180 с,
  переопубликование каждые 80 с).
- Риск: владелец выключен > 3 мин → имя свободно. Контакт, уже добавленный, хранится по NodeID и не затронут; новый —
  проверяется номером безопасности.

## 13. Исчерпание ресурсов и Sybil

### Ведро токенов (token bucket)
```
токены = min(burst, токены + rate · Δt);  запрос проходит, если токены ≥ 1 (и токены -= 1)
```
У нас: 5 сообщений/вызовов/предложений файлов в секунду, всплеск 30 — на NodeID отправителя.

### Пределы
| Ресурс | Предел | Почему по этому признаку |
|---|---|---|
| входящие соединения | 1024 всего, 64 с IP (кроме 127.0.0.1) | до рукопожатия NodeID неизвестен, а само рукопожатие — ресурс |
| хранилище DHT | доля публикатора 1/16 объёма; при переполнении — **вытеснение** давно не нужных (LRU) | отказ «ломал» честных; вытесняется тот, кто превысил долю |
| маршруты ретранслятора | 64 на инициатора | одна таблица на все туннели |
| файлы | согласие, 2/8 приёмов, квота | диск |

### Sybil и Eclipse
- **Sybil:** один участник создаёт много личностей. NodeID бесплатен → любой предел «на узел» обходится; доли
  выравниваются, честный узел опускается до «справедливой доли».
- **Eclipse:** атакующий окружает жертву своими узлами (заполняет её k-корзины) и контролирует, что она видит.
- Защиты (не реализованы): **доказательство работы** для NodeID (S/Kademlia: статическая и динамическая головоломки),
  **непересекающиеся пути** поиска (S/Kademlia), разнообразие подсетей в корзине, предпочтение долгоживущих
  контактов (в Kademlia уже есть — LRU, §2).

## 14. Данные на устройстве

### Конвертное шифрование (envelope encryption)
```
KEK (ключ шифрования ключей)      — в хранилище секретов ОС: Android Keystore / Secret Service / Keychain / Windows
 ├─ identity.key.enc               — ключ узла Ed25519, зашифрован KEK
 └─ HKDF(KEK, "p2p-overlay data at rest v1") → ключ-обёртка
       └─ history.keys             — ключ данных (DEK), сменяемый
             └─ history.jsonl      — каждая строка: enc1:<id ключа>:AES-256-GCM(DEK, запись)
```
- **Зачем два уровня:** сменить ключ данных — перешифровать историю, не трогая KEK и ключ узла; KEK никогда не
  покидает хранилище секретов.
- **Криптографическое удаление** (crypto-shredding): стёрли старый ключ — старые копии (резервные, удалённые
  файлы) больше не читаются.
- **HKDF** (RFC 5869): из одного секрета — независимые ключи для разных целей (параметр `info`).
- Права: каталог `0700`, файлы `0600` — как `~/.ssh` и `~/.gnupg`.
- **Срок хранения** — год: удалить / перешифровать и оставить / вынести в открытый файл (явное решение пользователя).

### Ошибки без адресов
Ретранслятор в release называет следующий узел `node:<16 hex>` без IP и причины: иначе инициатор, строя туннели через
разные узлы, узнаёт адреса и доступность чужих сетей (сканер «чужими руками»).

## 15. Голос поверх оверлея

### Конвейер
```
микрофон → Opus 16 кГц, кадр 20 мс, 24 кбит/с (60 Б/кадр), FEC
        → AES-256-GCM ключом звонка (одноразовые X25519 в подписанных INVITE/ACCEPT)
        → TUNNEL_MEDIA через ≥ 2 ретранслятора: без подтверждений, мимо очереди туннеля, окно повторов
        → джиттер-буфер → декодер / маскировка потерь (PLC) → смешивание участников → динамик
```
- **Почему не WebRTC:** WebRTC идёт напрямую (ICE/STUN) — мимо оверлея и ретрансляторов.
- **Без подтверждений:** опоздавший кадр голоса бесполезен, повтор только добавит задержку.
- **Групповой звонок** до 5 — «каждый с каждым» (mesh): n·(n−1) потоков; при 5 участниках это ещё дёшево, а
  центральный SFU стал бы точкой отказа и видел бы весь звук.

### Джиттер и буфер
- **Джиттер** (RFC 3550): `J += (|D(i−1, i)| − J) / 16`, где D — разница интервалов прихода и отправки.
- **Джиттер-буфер** держит кадры, чтобы проигрывать их ровно; глубже — меньше «заиканий», но больше задержка.
  Адаптивный буфер растёт при опозданиях и сжимается при спокойной сети (как NetEq в WebRTC).
- **PLC/FEC:** потерянный кадр восстанавливается из избыточности следующего (FEC Opus) или маскируется.

### Качество
- **Бюджет задержки** (ITU-T G.114): «рот — ухо» < 150 мс — хорошо, > 400 мс — неприемлемо.
- **E-модель** (ITU-T G.107): `R = 93,2 − Id − Ie,eff`, `Id ≈ 0,024·d` (при d < 177 мс),
  `Ie,eff = Ie + (95 − Ie)·Ppl/(Ppl + Bpl)`; `MOS = 1 + 0,035R + 7·10⁻⁶·R(R − 60)(100 − R)`.
  У нас: d = 68 мс, потерь 0, Ie = 10 → R ≈ 81,6 → **MOS ≈ 4,1** (сценарий `voice_call`).

## 16. Файлы: согласие и обманчивые имена

- **Предложение, а не поток:** сначала имя, размер, SHA-256; без согласия получателя на диск не пишется ни байта.
  Знакомый узел и ≤ 16 МиБ — автоматически; иначе вопрос. Квоты: 2 приёма от узла, 8 всего, общий объём автоприёма.
- **Целостность:** файл идёт блоками в E2E-конвертах; в конце — сверка SHA-256 всего файла.
- **Подмена имени (bidi spoofing):** символ U+202E (RIGHT-TO-LEFT OVERRIDE) разворачивает отображение:
  `счёт‮fdp.exe` выглядит как `счётexe.pdf`. Тот же класс — **Trojan Source** (CVE-2021-42574) в исходном коде.
  Защита у нас: настоящее расширение — отдельной меткой; скрытые символы в имени **исполняемого** файла —
  предупреждение с видимыми обозначениями и обязательное согласие. Сами символы не запрещены: они нужны письменностям
  справа налево.
