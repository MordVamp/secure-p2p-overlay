# Модель угроз

Область: P2P-оверлей в **LAN-стенде** (N=12–15 узлов, уровень simplified). Документ описывает, от чего защищает реализация, чем это подтверждено, и **чего она не делает**.

## 1. Активы

| Актив | Где живёт | Почему важен |
|---|---|---|
| Приватный Ed25519-ключ узла | `<state-dir>/` | определяет NodeID, подписи, TLS-сертификат, расшифровку сообщений |
| Содержимое сообщений | у отправителя и получателя | конфиденциальность и подлинность |
| Таблица маршрутизации / DHT-записи | память узла | целостность адресации |
| Метаданные: кто с кем общается | сеть, relay | приватность |
| История сообщений (тексты) | `<state-dir>/history.jsonl` (0600) | конфиденциальность переписки на диске |
| Псевдонимы `alias → NodeID` | DHT | к кому на самом деле уйдёт сообщение, отправленное по имени |

## 2. Модель противника

| Противник | Возможности |
|---|---|
| **Пассивный наблюдатель сети** | читает весь трафик (в т.ч. pcap) |
| **Активный MITM** | подменяет, вставляет, повторяет, задерживает пакеты |
| **Вредоносный relay** | участник туннеля: видит всё, что проходит через него, может отбрасывать/менять/дублировать |
| **Вредоносный узел DHT** | отвечает на FIND_NODE/FIND_VALUE ложью, публикует поддельные записи |
| **Вредоносный инициатор туннеля** | строит туннель со специально подобранными параметрами (петли, переполнение) |

Вне модели: компрометация ОС узла, физический доступ, побочные каналы, сговор большинства узлов.

## 4. Криптография

| Назначение | Примитив |
|---|---|
| Идентичность, подписи | Ed25519 |
| NodeID | SHA-256(0x01 ‖ pubkey) |
| Канал | TLS 1.3 (rustls, провайдер `ring`) |
| Канал (вариант `ake`, §11.3) | подписанный транскрипт Ed25519 + эфемерный X25519 → HKDF-SHA256 (ключи по направлениям) → AES-256-GCM, счётчик записей |
| E2E | эфемерный X25519 → HKDF-SHA256 → AES-256-GCM, случайный 96-бит nonce |
| Ключ получателя для E2E | выводится из его Ed25519 (Montgomery-форма / `SHA-512(seed)[..32]`) |

## Остаточные риски

Это **известные ограничения**, не скрытые дефекты.

| Риск | Суть | Смягчение / что делать |
|---|---|---|
| **Анализ трафика** | relay и наблюдатель видят размер, время и пары «кто с кем». Padding, cover traffic и микширование не реализованы | вне задач курсовой; не заявлять анонимность |
| **Sybil / Eclipse** | NodeID бесплатен; атакующий с множеством узлов может окружить жертву. Защиты нет (ни PoW, ни привязки к ресурсам) | ограничено LAN и малым N |
| **Squatting ключа** | чужой публикатор может занять ключ `node:<жертва>` данными без префикса `NREC1` (first-writer-wins), пока не истечёт TTL | TTL; потребуется отдельное правило для служебных ключей |
| **Squatting псевдонима** | имя достаётся тому, кто опубликовал первым; при разделении сети его могут занять двое; после ухода владельца имя освобождается через TTL | сверять NodeID собеседника при первом контакте (TOFU) |
| **История на диске** | `history.jsonl` хранит тексты открыто (права 0600), ротации нет | та же граница доверия, что у `identity.key`; шифрование и ротация — доработка |
| **Forward secrecy E2E** | эфемерный ключ только у отправителя; компрометация долговременного ключа получателя раскрывает ранее перехваченные сообщения | двусторонний ratchet (не реализован) |
| **TLS-контекст общий на процесс** | `rpc::install_tls` — один на процесс; допущение «один узел на процесс» | не запускать несколько узлов в одном процессе |
| **Окно анти-replay зависит от часов** | сообщение принимается, если его метка времени не старше 10 мин и не опережает часы больше чем на 2 мин; сильно расходящиеся часы узлов ведут к отказам | синхронизация времени (NTP) |
| **AKE не скрывает идентичность** | в собственном рукопожатии NodeID и ключи сторон передаются открыто (TLS 1.3 шифрует сертификаты) | вне задач работы |
| **`/api/send_file` читает любой файл** | без `P2P_API_TOKEN` (desktop, веб-панель) API не аутентифицирован: процесс, достучавшийся до 127.0.0.1, может отправить любой файл, доступный узлу | не пробрасывать порт API; на Android токен включён всегда |
| **Метаданные «печатает» и «прочитано»** | собеседник узнаёт, когда вы набираете текст и открыли сообщение; ретрансляторы видят дополнительные конверты (размер и время) | обе функции — опции, выключаются в настройках; «печатает» уходит только по уже открытому туннелю |
| **Почтовый ящик: затирание и метаданные** | хранитель реплики может удалить или заменить запись своей (получатель её отбросит — подпись не та), т.е. задержать доставку; ключ ящика `mbox:<получатель>:<отправитель>` показывает хранителям, кто кому пишет; запись живёт, пока отправитель в сети (republish) | репликация R=3; повторная отправка при следующем контакте; анонимность не заявляется |
| **«Только клиент» уменьшает сеть ретрансляторов** | чем больше узлов в режиме экономии, тем меньше выбор relay и проще наблюдать трафик | режим по умолчанию — «Обычный» (ретранслятор) |
| **Группы без управления составом** | состав задаёт создатель и он едет в каждом сообщении; исключить участника, у которого уже есть состав, нельзя (он может писать в группу) | групповые ключи и управление составом — доработка |
| **Флаги внесения отказов** | `--fault-drop`, `--fault-delay-ms` делают узел неисправным ретранслятором — только для экспериментов; узел предупреждает в журнале | не использовать вне стенда |
| **Веб-панель без аутентификации** | `127.0.0.1`, без логина; любой локальный процесс может отправлять сообщения от имени узла | не пробрасывать порт; рассматривать токен |
| **Хранение ключа на компьютере** | на ПК приватный ключ лежит файлом без шифрования (на Android — зашифрован ключом Keystore); узел умеет шифровать ключ через `P2P_IDENTITY_KEK`, но desktop этим пока не пользуется | права на каталог `state/`; связка с хранилищем ключей ОС — доработка |
| **DoS** | нет ограничения скорости запросов на один узел и числа входящих соединений; с пулом (`reuse_connections`) окно больше: простой соединения до 60 с, до 64 запросов соединения одновременно, одно рукопожатие на много запросов | не заявляется; без пула сервер ведёт себя как раньше; лимиты — доработка (TRANSPORT_OPTIONS §8) |
| **Пул: «голова очереди» и полуоткрытые соединения** | все запросы к соседу — в одном TCP: потеря пакета или большой блок файла задерживает остальные; сосед, пропавший без разрыва, стоит одного тайм-аута | после тайм-аута ответа соединение закрывается; приоритеты, keepalive, QUIC — доработка |
| **Совместимость** | форматы подписи записей (`v2`) и `TUNNEL_DATA` менялись; старые узлы несовместимы | обновлять сеть целиком |

## 5. Проверка захватом трафика (pcap)

`p2p-orchestrator scenario pcap`: `dumpcap -i lo` на портах оверлея во время 5 сообщений и 5 DHT STORE с уникальным маркером;
маркер в захвате **не найден**, весь полезный трафик — TLS (в ServerHello согласован TLS 1.3). Положительный контроль: тот же
маркер находится в открытом localhost-HTTP панели узла — метод поиска работает. Результат — `experiments/results/pcap_no_plaintext/`.
Ограничение: проверяется только отсутствие известной строки, а не стойкость шифрования; метаданные (размеры, время) видны.

## 6. Что не доказано

- Нет формальной верификации протокола; схема E2E — стандартная (sealed box / ECIES), но собрана вручную из примитивов, **независимого аудита не было**.
- Анти-replay и устойчивость к DoS проверены только модульными тестами и LAN-прогонами.
